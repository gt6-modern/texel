# v1/cases/negative/neg-png-asset-not-png

- 形态:`negative` 负例(PXL.md §13.3);`defect: png`
- **受测侧**:阶段 R2(§11.2 阶段表第 12 行:按 §9.3 的顺序解析**被选中**的依赖)
- 受测输入:`entry.pxl` + `art/tile.png`(18 字节 ASCII 文本,不是位图)
- 期望错误码:`PXL009`(见 `expected.error`,一行 + LF)
- 缺陷数量:**1**(声明的 `kind` 与实际字节不符)

## 覆盖条款

- §11.1 的 `PXL009` 定义含「声明类型**与实际资源不符**」;
- §11.1 的边界句(与 `PXL006` 的分界):**声明的 `kind` 与该资源的实际字节不符 → `PXL009`**
  ——本用例的素材连 PNG 签名都没有,正落在这一侧;
- §8.3:有**正确签名**但结构非法才归 `PXL006`;本用例签名就不对,故不是 `PXL006`;
- §9.1:只有被当前 target 实际选中的声明才会被读取 —— 所以 `entry.pxl` 必须 `stamp` 它,
  否则这条永远走不到解析(与 `neg-path-escape-root` 的“声明校验独立于选中”正好互补);
- §11.2:阶段 R1 的路径语法校验先通过(`art/tile.png` 全小写、无 `..`),错误落在 R2。

## 缺陷(只有这一处)

素材字节是 `this is not a png\n`。路径合法、`kind` 是 `"png"`、`assets` 成员集合合法、
`stamp` 恰好给了 `asset` —— 唯一的错就是“声明是 PNG,字节不是”。

## 与 neg-png-asset-structure-invalid 的一对关系

两条用**同一个** `entry.pxl`、只换素材字节:本条无签名 → `PXL009`;那条有签名但缺
`IDAT`/`IEND` → `PXL006`。两条合起来把 §11.1 的边界钉成可判定事实;
只留一条时,两侧实现会各自按“PNG 相关错误一律 `PXL006`”或“一律 `PXL009`”分叉
——这正是第四轮审查 R4-03 报的分歧。

## 判定方式

实现必须以 `PXL009` 失败,且不产出任何输出文件(§13.3 / README §7.2)。
`expected.error` 只写码,不含说明文字。

## 与 v0 的差异

v0 没有外部 asset:它的 `PXL006` 只覆盖“读到了但 PNG 非法”;“声明类型不符”这一维在 v0 里
不存在。`PXL009` 是 v1 新增码。
