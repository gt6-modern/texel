# PXL — 像素素材描述格式

**Wire version：1** · **软件首发版本：0.1.0** · **性质：规范性文本**

本文件是 PXL 的中文权威规范；英文译本为 [`PXL.en.md`](PXL.en.md)。两者冲突时以本文件为准。当前公开格式只接受 `"version": 1`；`0..65535` 内其他整数版本报 `PXL007`，缺失、非整数、负数、超域或不可表示版本报 `PXL001`。

本文把单文档像素语义与静态依赖/有限参数语义合并成一份完整规范。`Core §` 定义每份文档的光栅、PNG 与确定性规则；`Extension §` 定义当前文档模型、assets、bindings、resolver、依赖图和会话预算。Extension §3 的顶层字段集合优先于 Core §3 中较窄的单文档字段描述；其余 Core 规则全部适用。

## Version dispatch

1. 严格解码 UTF-8 并解析单一 JSON 对象；重复成员名为 `PXL001`。
2. `format` 必须是字符串 `PXL`。
3. `version` 必须是可表示的十进制整数。值 `1` 进入本文完整流程；域内其他值为 `PXL007`；域外或类型错误为 `PXL001`。
4. 实现不得接受 version 0，也不得通过隐式迁移改变输入文档。

# Part I — Core pixel semantics

## Core §1. 状态与定位

PXL 是**位图的无损文本镜像**:把一张 RGBA 位图写成可读、可 diff 的文本,再把该文本还原成逐像素相同的位图。

**PXL 不是任何项目的贴图真源。** 上线资源仍然是 PNG;本格式只承担读取、镜像与回渲。因此:

- PXL **不进任何构建流水线**,不产出进入其它项目资源包的文件,不挂任何项目的 `check` / datagen / CI 门禁。
- 本仓库自己的测试只跑自己的代码与 `spec/conformance/` 语料。
- 本规范**与实现语言无关**:第 2 至 12 章不出现任何编程语言的专有概念、库名或语言特性。文中"实现"一词只表示"任一符合本规范的抽取器或渲染器"。
- **唯一的例外是 §13**:语料生成器的入口路径、命令与运行时必须写死到"换个人也能跑出同样字节"的程度,否则 §13.6 的生成型用例不可执行。因此 §13 会出现具体语言与命令——那属于**仓库工具链**,不属于格式本体,不影响前一条。

current core 是草案。附录 C.3 有两类条目,处置方式不同:

- **已落地的假设**(`C-4`、`C-5`、`C-7`):`AGENTS.md` 留了空,规范必须给一个值,否则 `expected.pxl` 不唯一、实现方无从下手。这类条目规范**照下面写定的值定义行为,实现方可直接实现**;你若要换值,改规范一处即可,代价写在表里。
- **已解决**(`C-6`、`C-8`):`AGENTS.md` 已按实测与裁决同步,两份文档不再分叉。

无论哪一类,**实现方都不得在规范之外另选值**。

### Core §1.1 与 AGENTS.md 的关系:冲突时以本规范为准

本仓库有两份写"必须"的文档:`AGENTS.md`(项目宪章)与本规范。作为**常设规则**,两者不一致时:

1. **数值不一致 → 以本规范为准。**
2. **能力要求 vs 具体算法 → 两者都成立,不构成冲突。** `AGENTS.md` §3.3 要求"抽取器必须做图元压缩",这是**能力**要求;本规范附录 A 钉的是**算法**(`MIN_RUN = 3`、全局回退、块切分顺序)。后者是前者的可判定化。**实现按附录 A。**
3. 其余一切不一致,一律以本规范为准,并在附录 C 记录;**不得由实现方任选**。

**当前状态:两份文档已无已知冲突。** 历史上的一处——`AGENTS.md` §3.2 曾把 `index4` 上限写作 `65536`,与本规范 §4.1 的 `65535` 相悖——已在 `AGENTS.md` 就地更正(四位十六进制共 65,536 个值,`0000` 保留给透明 slot,故上限 65,535);§7 的三处素材数字、以及一行指向不存在目录的素材,也一并按实测更正。

保留本条不是为了追究已修的问题,而是因为**下一次分叉一定还会发生**:只要有两份文档都在写"必须",就迟早会出现两个数字。届时按上面三条处置,不必重新讨论。

### Core §1.2 用途

只有两个,别的都不承诺:

1. **审查**:一次贴图改动在文本里表现为"某个图层、某个坐标上的一个 token",而不是"二进制块变了"。
2. **人工 / agent 编辑**:改一个像素等于改一个 token;坐标可指、可 review、可回滚。

## Core §2. 术语

| 术语 | 定义 |
|---|---|
| **texel** | 位图的单个像素,值域为 RGBA 四通道各 8 bit。本规范中"像素"与 texel 同义。 |
| **palette slot**(slot) | 调色板中的一个位置编号。slot 0 **保留给透明**,不占用 `palette` 数组;非透明 slot 为 1 到该档上限。同一 slot 在全文只对应一个 texel 值。 |
| **encoding tier**(档) | 三档 token 宽度之一:`char` / `index` / `index4`。**一个文件只用一档**,全文 token 宽度恒定。 |
| **layer**(图层) | 一块 `width` × `height` 的像素缓冲,由若干 op 依序绘制得到。图层之间按 `blend` 自下而上合成。 |
| **op**(图元) | 对当前图层缓冲的一次确定性写操作。全文共八条,见 §5。 |
| **sprite** | 文档内以名字引用的一段 token 矩形,只能被 `stamp` 读入图层,自身不参与合成。 |
| **transparent slot** | slot 0。其 texel 值恒为 `00000000`。三档中分别记作 `.`、`00`、`0000`。 |

**用词约定**:"必须 / 不得"为强制;"应"为在无特殊理由时必须遵守,偏离要在此文档记录理由;其余为说明。

## Core §3. 文档模型

### Core §3.1 文件形态

一个 PXL 文件就是**一个 JSON 文档**。

- 编码:UTF-8,不带 BOM。
- 换行:LF(U+000A),不得含 CR。
- 缩进:2 空格,不得使用制表符缩进。
- 文件必须以单个 LF 结尾。
- 行尾不得有空白。
- 每个对象的每个成员各占一行,**且成员顺序固定**(§3.7)。为节省篇幅,**本规范正文里的示例片段**把 op 对象写成单行;规范形式仍是一 key 一行且顺序如 §3.7。

> 只钉"一 key 一行"是不够的:两个实现可以把成员排成不同顺序、两者都合法,而 `expected.pxl` 的"零 diff"必然失败。因此 §3.7 把成员顺序也钉死。

### Core §3.2 顶层字段

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `format` | string | 是 | 恒为 `"PXL"`。缺失、类型不是字符串、或值不等于 `"PXL"` 均为 `PXL001`(阶段 3)。 |
| `version` | integer | 是 | 恒为 `0`。见 §12。 |
| `encoding` | string | 是 | `"char"` / `"index"` / `"index4"`。见 §4。 |
| `width` | integer | 是 | 像素宽,取值 1..65536。 |
| `height` | integer | 是 | 像素高,取值 1..65536。 |
| `palette` | array of string | 是 | 非透明颜色表。`palette[i]` 是 slot `i+1` 的 texel 值。**三层判据,不要混**:项不是字符串 → `PXL001`(阶段 3,类型类别);是字符串但不匹配 `^[0-9A-F]{8}$`、或含 `00000000`、或长度超过上限 → `PXL005`(阶段 9);长度 `>= 65536` → `PXL003` 不适用(§4.5),直接 `PXL005`。 |
| `sprites` | object | 否 | 名字 → token 行数组。省略等价于空对象。 |
| `layers` | array of object | 是 | **至少 1 个图层**,自下而上排列。空数组即 `PXL001`(阶段 3)——它不是"没有图层",而是缺了必需内容;图层**数量**上限另由 §5.0.2 管,超限报 `PXL002`(阶段 6)。 |

顶层出现上表之外的字段即为 `PXL001`。其中 `variant` 与 `bindings` 是**有意保留**的字段,含义见 §12:在 current core 中它们同样触发 `PXL001`(fail-closed)。

**本文件内任何对象(顶层、图层、op、`from` / `to`、`sprites`)的成员名都不得重复**;重复即 `PXL001`。这一条不只是洁癖:不同 JSON 解析器对重复键有的取首值、有的取末值、有的直接报错,两个 `width` 或两个同名 sprite 会让同一份文本得到不同像素。

### Core §3.3 图层与 op

图层对象字段:

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `name` | string | 是 | 图层名,在文档内唯一,匹配 `[a-z][a-z0-9_-]*`。仅供人读与 diff 定位,不参与语义。 |
| `blend` | string | 是 | `"normal"` / `"multiply"` / `"mask"`。见 §6。 |
| `ops` | array of object | 是 | 依序执行,可为空数组(等于该层全透明)。 |

每个 op 对象必须有 `op` 字段命名八条图元之一;op 对象不得有该条图元未定义的字段。

### Core §3.4 `grid` 的行数组格式

凡出现 token 行数组的地方(即 `grid` op 的 `grid` 字段与 `sprites` 的每个值),强制:

- 一个数组元素 = 一行。元素内**只允许出现 §4.2 / §4.3 枚举出的 token 字符**;任何其它字符——空格、制表符、换行符、**U+00A0 等非断行空格**、以及任何控制字符——一律非法。**不要用宿主语言的"是否为空白"分类来判定**:不同实现对 U+00A0 这类码点的分类不同,照语言分类就会让同一份文件在两处得到 `PXL001` 与 `PXL003` 两个答案。规范只认枚举出的字符集。
- **行数组至少 1 行**。空数组(如 `"grid": []`,或某个 sprite 的值为 `[]`)即 `PXL001`——没有"0 行矩形"这种东西。
- **每行至少 1 个 token**。空串行(如 `"grid": [""]`)即 `PXL001`——同样没有"0 列矩形"。
- **同一数组内所有行长度必须相等**。
- **长度一律按 JSON 解码后的 Unicode 码点计数**:不按字节,也不按 UTF-16 代码单元。一个转义代理对(`\uD83D\uDE00`)解码后是**一个**码点,算 1 个字符。这条对上面的"各行等长"(阶段 3)与下面的"整除性"(阶段 5)同时生效。必须写死:否则 `["\uD83D\uDE00", "00"]` 按码点是不等长(1 vs 2,阶段 3 报 `PXL001`),按 UTF-16 代码单元是等长(2 vs 2,滑到阶段 4 报 `PXL003`)——同一份文件两个答案。
- 行长的**字符数**(按上一条的码点口径)必须是 token 宽度(1 / 2 / 4)的正整数倍;其对应的 **token 数**(即该行的像素列数)必须在 **1..65536** 之内(下界是 1,不是 0)。这两个数不同:`index4` 档下一行最多 65536 × 4 = 262144 个字符。**上界限制的是 token 数,不是字符数**——否则 `index4` 与 65536 宽的画布会自相矛盾(见 `PXL002`)。
- 由上面两条可推出:**任何 `grid` 或 sprite 的尺寸恒为「列数 × 行数」且两者都 ≥ 1**,所以 §5.5 / §5.8 所说的"矩形"总有确定尺寸,不会退化成 0×0。这一条是刻意选的**严格语义**:画布 `width`/`height` ≥ 1,规范抽取器也永远不会产出空行或空数组,允许 0 宽只会给每个实现增加一个必须特判的分支,而换不来任何表达能力。
- 每段 token 必须能按 §4 解码;任何一段解不出即报错。

### Core §3.5 完整最小示例:4×4,两色,四角透明

像素内容(slot 视角,`.` 为透明):

```
0..0
.11.
.11.
0..0
```

调色板按行优先首次出现顺序分配:第一行第一个 `0` 是第一个非透明色 → slot 1;第二行第一个 `1` 是第二个 → slot 2。设 slot 1 = 纯红,slot 2 = 纯绿。规范形式的完整文档:

```json
{
  "format": "PXL",
  "version": 1,
  "encoding": "char",
  "width": 4,
  "height": 4,
  "palette": [
    "FF0000FF",
    "00FF00FF"
  ],
  "layers": [
    {
      "name": "base",
      "blend": "normal",
      "ops": [
        {
          "op": "grid",
          "x": 0,
          "y": 0,
          "grid": [
            "0..0",
            ".11.",
            ".11.",
            "0..0"
          ]
        }
      ]
    }
  ]
}
```

该文档的规范抽取结果**就是**上面这段文本(见附录 A 的判定规则:四行都含长度小于 3 的同色段,故整图落为一个 `grid` op)。

### Core §3.6 index4 片段

同一个格式在 `index4` 档下,token 宽度为 4。下面片段取自一张 300 色的图,画 **2×2**(2 行,每行 2 个 token,共 8 个字符):

```json
{ "op": "grid", "x": 0, "y": 0, "grid": ["0001012C", "00FF0000"] }
```

解码:`0001` = slot 1 = `palette[0]`;`012C` = slot 300 = `palette[299]`;`00FF` = slot 255 = `palette[254]`;`0000` = 透明。**token 不得越过 `palette` 长度**:这张图只有 300 色,最大合法 token 就是 `012C`——早前示例用了 `0A2F`(slot 2607),那种 slot 根本不可能出现在 300 项调色板里。

注意一行里可以并排多个 token——**行是一段字符串,不是 token 数组**,所以"行长"指字符数,"列数"指 token 数(§3.4)。

### Core §3.7 规范序列化(逐字节可判定)

"零 diff"要求成员**顺序**也固定,否则两个各自合法的输出仍不相等。规范形式规定:

- 顶层成员顺序:`format`、`version`、`encoding`、`width`、`height`、`palette`、`layers`;有 `sprites` 时排在 `palette` 与 `layers` 之间。
- 图层成员顺序:`name`、`blend`、`ops`。
- op 成员顺序:`op` 恒为第一个,其后按下表;不得有多余成员。

| op | 成员顺序 |
|---|---|
| `fill` | `op`, `slot` |
| `rect` | `op`, `x`, `y`, `w`, `h`, `slot` |
| `pixel` | `op`, `x`, `y`, `slot` |
| `line` | `op`, `x0`, `y0`, `x1`, `y1`, `slot` |
| `grid` | `op`, `x`, `y`, `grid` |
| `mirror` | `op`, `from`, `to`, `flipX`, `flipY` |
| `erase` | `op`, `x`, `y`, `w`, `h` |
| `stamp` | `op`, `sprite`, `x`, `y`, `flipX`, `flipY` |

- 嵌套对象成员顺序:`from` = `x`, `y`, `w`, `h`;`to` = `x`, `y`。
- **可选布尔成员当且仅当为 `false` 时省略**:`mirror` / `stamp` 的 `flipX`、`flipY` 只在为真时出现。写 `"flipX": false` 仍**合法**,渲染器必须接受,但它**不是**规范形式。
- 空数组写成一行:`"ops": []`、`"palette": []`。
- 整数按十进制书写:无前导零、无小数点、无指数、无正号。
- 数组元素(每个调色板项、`grid` 的每一行)各占一行。
- **冒号前无空格、冒号后恰一个空格**:`"width": 4`。`"width":4` 与 `"width":  4` 都不是规范形式。
- 成员与元素之间以 `,` 结束上一行;**不得有尾逗号**(JSON 本身也不允许)。
- **对象的花括号位置按上下文分三种**,不能一句话概括:
  - **顶层对象**:`{` 独占第一行,`}` 独占最后一行,两者同列;成员缩进 +2。
  - **作为成员值的对象**(如 `mirror` 的 `from` / `to`、顶层 `sprites`):`{` **紧跟在该成员的 `": "` 之后留在同一行**;其成员缩进 = 该键所在行的缩进 + 2;`}` 独占一行、与该键同列。若把 `{` 挪到下一行,那一行会以 `:` 结尾——于是"冒号后恰一个空格"与"行尾不得有空白"两条必破其一,规范形式就不可写了。
  - **作为数组元素的对象**(如 `layers` / `ops` 里的对象):`{` 独占一行(缩进同该元素),成员再 +2;`}` 独占一行、与 `{` 同列。
  这三种写法合起来恰好等于"2 空格缩进的 JSON 序列化"的输出;规范不另立一套排版。
- 非空数组:`[` 紧跟在其成员的 `: ` 之后留在同一行,元素缩进为当前层级 +2,`]` 独占一行并与该成员键同列。空数组写作 `[]`。
- 字符串:文档内容只用到 U+0020..U+007E 内的可打印 ASCII(`0-9A-F`、`a-y`、`.`、以及固定的键名与枚举值),因此规范形式**一律原样书写,不使用任何转义序列**;含反斜杠或需要转义的字符只会出现在注释性的 `notes.md` 里,不在 PXL 里。
一个含嵌套对象的 op 的规范形式(取自工具用例 `op-mirror-overlap`,注意 `from` / `to` 的 `{` 都在键同行):

```json
        {
          "op": "mirror",
          "from": {
            "x": 0,
            "y": 0,
            "w": 8,
            "h": 4
          },
          "to": {
            "x": 8,
            "y": 0
          }
        }
```

- **`sprites` 的成员名**必须匹配 `[a-z][a-z0-9_-]*`(与图层名同一条语法),在文档内不得重复;规范形式下**按名字的 ASCII 字节序升序**排列。不排序就没有唯一字节形式——而 `op-stamp-flip` 这类用例必须带 `sprites`,它一旦不唯一,仅渲染正例的输入也就没有规范写法了。
- 除上列成员外**不写任何成员**;规范抽取结果不含 `sprites`(它只产 `fill` / `rect` / `grid`)。

### Core §3.8 渲染器的接受集(严格宽于规范形式)

§3.1 与 §3.7 描述的是**抽取器必须产出的规范形式**。渲染器**不得**要求输入是规范形式——否则任何编辑器顺手改一下空白,PXL 就打不开了,§1.2 的"人工 / agent 编辑"用途直接作废。

渲染器**必须接受**:任何能按 UTF-8 解码的文本(允许并忽略 BOM),只要是合法 JSON 且满足 §3.2 / §3.3 / §3.4 / §3.7 的**成员集合**规则,即:

- 任意缩进、任意换行风格(含 CRLF)、任意行尾空白、有无结尾换行,均可;
- 任意成员顺序;
- 等值的数值字面量,如 `4` 与 `4.0` 都表示整数 4(值必须整数值,见 §11 `PXL002`)。
- **整数性与区间必须按数字的原始词法做精确十进制判断,不得先转成二进制浮点。** `1.0000000000000001` 与 1 不相等,是 `PXL002`;而常见的双精度解析会把它舍成 `1.0` 从而误接受。`65536.0000000000001` 同理,不得当成 65536 放过。
- 可选布尔成员写成 `false` 与整体省略等价。

只有不满足上述条件的输入才按 §11 报错。**"不符合 §3.7" 不是拒绝理由**——它只决定抽取器能否与 `expected.pxl` 零 diff,与"这份文档是否合法"是两件事。

## Core §4. 三档编码

### Core §4.1 档位与容量

| encoding | token 宽度 | 透明 token | 非透明 slot 范围 | 非透明色数上限 |
|---|---|---|---|---|
| `char` | 1 字符 | `.` | 1..61 | 61 |
| `index` | 2 字符 | `00` | 1..255 | 255 |
| `index4` | 4 字符 | `0000` | 1..65535 | 65535 |

三档上限都是**该 token 宽度可表示的值域总数减 1**,被减的那个值固定留给透明 slot 0。这是三档共用的同一条算术,不是三个独立数字。

### Core §4.2 `char` 档的字符集

slot `k`(1 <= k <= 61)的 token 是下表第 `k` 个字符(1 起始):

```
0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxy
```

即 `0-9` + `A-Z` + `a-y`,共 61 个。`.` 保留给透明;`z` **保留未用**。`char` 档出现 `.` 与上表 61 字符之外的任何字符(含 `z`、空格、别的标点)即 `PXL001`。

### Core §4.3 `index` / `index4` 档

slot `k` 的 token 是 `k` 的十六进制,宽度分别为 2 / 4,**大写**、零填充。小写字母即 `PXL001`。

### Core §4.4 调色板分配(规范形式)

非透明 slot **按行优先、首次出现顺序**分配:从 `(0,0)` 起逐行、行内从左到右扫描最终像素网格;第一次见到的非透明 texel 值取 slot 1,第二次不同的值取 slot 2,依此类推。**透明 slot 0 不参与该顺序。**

### Core §4.5 何时必须升级到下一档

设 `n` = 本文档 **`palette` 数组的长度**。这是渲染器唯一可判定的读法:能不能用更窄的 token,取决于**容量**而不是某个成员恰好被引用了几次。档位由 `n` 唯一决定,没有选择余地:

- `n <= 61` → `char`
- `62 <= n <= 255` → `index`
- `256 <= n <= 65535` → `index4`
- `n >= 65536` → 拒绝,`PXL005`

判定规则(可由测试直接验证):**文档声明的 `encoding` 必须等于由 `palette` 长度派生出的值**;不等即 `PXL003`。抽取器不"选择"档位,只派生;渲染器不"猜"档位,只校验。

**这条只在 `n <= 65535` 时有定义。** `n >= 65536` 时上表根本没有可派生的档位,"声明值是否等于派生值"这句话无从判断——此时**跳过档位比对**,由 §11.1 阶段 9 报 `PXL005`。不写死这一条,同一份 palette 超容量文档就可能被一个实现报 `PXL003`、被另一个报 `PXL005`,两者各自都能引经据典。

**`palette` 长度超过声明档的上限,不单列一条拒绝规则**:长度一旦超过声明档的上限,派生档必然**高于**声明档(三档是单调的),阶段 7 的档位比对必然会先命中 `PXL003`。所以"长度超过该档上限"是条**不可达**的条件,写进 `PXL005` 只会制造两条都"合规"的规则。`PXL005` 只保留真正独立的容量错误:`n >= 65536`(根本没有档位可派生)。

这里有一个必须钉死的细节:规范抽取器**不产出未被引用的调色板项**(§3.7),所以对规范输出而言 "`palette` 长度" 与 "源图非透明色数" 是同一个数;但对人工编辑的文档,只有前者可判定。若按"被引用的色数"判定,一份 `palette` 有 100 项、实际只用 2 项的 `index` 文档会先通过校验,再让那 98 个空位的存在无从解释。因此:以 `palette` 长度为准;未引用项**合法**但**非规范形式**。

由此可推出两条必测性质:

- 恰好 61 色的图必须是 `char`,62 色必须是 `index`。
- 恰好 255 色的图必须是 `index`,256 色必须是 `index4`。

### Core §4.6 一个文件只用一种 token 宽度

同一文件内 `encoding` 恒定,因此 token 宽度恒定。**解析是按这个固定宽度逐段位置切分的**——`index` 档下 `"0001"` 只能切成 `00`、`01` 两个 token,不存在"这个 token 有多宽"的判定空间。

所以早先写的「混合宽度即 `PXL001`」「token 长于本文档 token 宽度」都是**空话**:前者不可能发生,后者无法表达。需要拒绝的只有一种情况——某行字符数不是 token 宽度的正整数倍(如 `index` 档下 `"000"`,第二段只剩 1 个字符),报 `PXL001`。

## Core §5. 图元(八条)

### Core §5.0 通用规则

- 坐标系:原点 `(0,0)` 在**左上角**,`x` 向右增,`y` 向下增。单位是像素,不是 token。
- **整数域封闭**:文档里所有整数成员都必须落在 §5.0.1 给出的闭区间内,越界即 `PXL002`。
- **终止性**:端点受 §5.0.1 的上界约束,`line` 的步进轮数不超过 `|dx| + |dy| + 1 <= 262145`,必然终止。实现**不得**为省时间先做解析裁剪(如 Liang-Barsky)再画——那会得到与逐点裁剪不同的像素集;正确做法就是逐点算、逐点丢。
- op **只写当前图层缓冲**。op 之间不合成、不混色:一条 op 把目标位置的 texel 值**整体替换**为该 op 指定的 slot 值(含 RGBA 四通道)。混合只发生在图层之间(§6)。
- 每条 op 的 `slot` 是整数,取值 `0..65535`;必须不大于该档上限且不大于 `palette` 长度,否则 `PXL005`。`slot: 0` 合法,表示写透明。
- **越界一律裁剪,不报错。** 落在 `[0,width) x [0,height)` 之外的写入被丢弃;部分越界的矩形/线段只写重叠部分;完全越界等于空操作。任何 op 都不因越界失败。
- **禁止抗锯齿。** 任何 op 都不产生"半覆盖"像素、不产生中间色、不做采样。一条 op 要么把某个像素整体设成某 slot,要么完全不动它。
- 矩形一律**右开、下开**:`rect(x,y,w,h)` 覆盖 `x <= px < x+w` 且 `y <= py < y+h`。`w` 或 `h` 为 0 等于空操作;为负即 `PXL002`。

### Core §5.0.1 整数域与中间量上界

| 成员 | 范围 |
|---|---|
| `width`、`height` | 1..65536 |
| `x`、`y`、`x0`、`y0`、`x1`、`y1`(含 `from` / `to` 内的) | -65536..65536 |
| `w`、`h`(含 `from` 内的) | 0..65536 |
| `slot` | 0..65535 |

表里的成员名分两类:`width` / `height` 是**文档级字段**,其余是**八条已知图元的参数**。`op` 名不在八条之内的对象,其同名字段**不参与本表检查**——一个未知 op 的 `x` 究竟是不是坐标无从判断,照名字硬卡区间只能靠猜。理由与优先级见 §11.1。

为什么必须封顶 —— 不是形式主义:

1. **整数宽度差异**。任意精度整数实现与固定宽度整数实现,对同一个大坐标算 `x+w`、`abs(x1-x0)`、`2*err` 会得到不同结果:前者不会溢出,后者会回绕。两个实现就此分叉,而且分叉发生在最不容易被小图测出来的地方。本规范不假定实现用哪一种,而是把取值域收窄到两者都能精确表示的范围。
2. **终止性**。`line` 是逐点步进的;若端点可以是 10 的任意次幂,一条完全在画布外的线也会让循环跑到不可接受的长度。

由上表可**证明**:上面这些**坐标与颜色**运算的中间量都落在 32 位有符号整数范围内,故任意精度实现与固定宽度实现在此范围内逐位相同:

```
|x1 - x0| <= 131072      err = dx + dy  =>  |err| <= 262144      2*err <= 524288
x + w     <= 131072      合成用的 cNum       <= 33162750
全部远小于 32 位有符号整数上界 2^31 - 1 = 2147483647
```

**这个保证只覆盖坐标与颜色运算,不覆盖 §5.0.2 的资源校验。** `width × height` 在宽高各自合法时可以到 `65536 × 65536 = 4,294,967,296`,**超过 2^31 − 1**;用 32 位算这个乘积会回绕成 `0`,于是一份 65536 × 65536 的文档会**通过**面积检查。

所以 §5.0.2 的每一项——面积、图层数 × 面积、每层 ops 数、文档字节数——都必须用 **64 位或任意精度整数**,或改用**不产生乘积的比较**(例如判 `width × height > 2^22` 时先比 `width > 2^22 / height`)。**不得依赖 32 位乘法。** 这不是理论风险:回绕恰好把"超限"变成 `0`,而 `0` 永远通过。

越界不是「夹到边界」,而是**报错**(`PXL002`):静默夹取会让文档内容与作者意图不一致,而作者下次才发现。

### Core §5.0.2 面积上界与资源语义

宽与高各自到 65536 并不等于两者可以同时到 65536:`65536 × 65536 = 4,294,967,296` 像素,单个 RGBA8 缓冲就是 **16 GiB**。而每个图层又是一个完整缓冲,`ops` 与 `sprites` 不限量的话,一份"合法"文档可以要求任意多内存。

但上界光"实现装得下"是不够的,还须满足第二件事——**任何被接受的输入,按附录 A 抽取后仍然合法**。上一版漏掉的正是这一条,于是出现两个反例:

- `65535 × 4`、段宽恒为 3、相邻行反色的双色图(面积 262,140,合法):四行都是 RUNNER 且上下不可合并,附录 A 必须产出 `21845 × 4 = 87,380` 条 `rect`,超过每层 65,536;
- `4096 × 4096`、256 色、全 GRID 的图(index4):光 token 字符就是 `2^24 × 4 = 67,108,864` 字节,**恰好等于**整份文档上限,加上 JSON 开销必然超限。

两种输入尺寸、面积、色数全部合法,却抽不出合法输出;而抽取器既不能输出非法文档,也没有拒绝路径。因此上界必须是**一组互相封口**的数字:

| 项目 | 上界 |
|---|---|
| `width × height`(总像素数) | 2^22 = 4,194,304(相当于 2048 × 2048) |
| 图层数 | 256 |
| 图层数 × `width × height` | 2^24 = 16,777,216 像素(全部缓冲合计 64 MiB RGBA8) |
| 每层 `ops` 数 | 32,768(由附录 A 的**全局回退**保证,不靠运气) |
| `sprites` 个数 | 4096 |
| 每个 sprite 的行数 | 65536 |
| 文档 UTF-8 字节数 | 67,108,864(64 MiB) |
| 光栅工作(裁剪后像素写入总数) | 2^22 = 4,194,304(见下条) |

**光栅工作预算(2^22)为什么必须单列。** 面积、图层数、每层 ops 数各有上界,并不蕴含渲染成本可控:
一份 2048×2048 的画布配 1,000 条全屏 `rect`,三个上限都合法,累计要做 41 亿次像素写入
(实测 4.7 秒;32,768 条可达分钟级)。因此再加一条**确定性的**预算——所有图层的所有 op
**裁剪之后**的像素写入次数之和不超过 2^22,计数口径与实际写入一一对应:

- `fill` / `rect` / `erase`:与画布求交后的 `宽 × 高`;
- `pixel`:命中画布记 1,否则 0;
- `grid`:与画布求交后的 `token 列数 × 行数`;
- `stamp`:与画布求交后的 `sprite 列数 × 行数`;
- `line`:步数 `max(|dx|,|dy|) + 1`(越界点仍走一步,**不**打折);
- `mirror`:`to` 矩形与画布求交后的面积(读侧按目标侧计)。

超限报 `PXL002`。现有语料里最大的合法值是 262,144(`syn-grid-large-index4`),余量 16 倍。
这个上界是**格式边界**,不是性能建议:同一份文档在任何实现上都该被接受或拒绝。

**不变量(本节这些数字的来源)**:任何被 §8.1 接受的输入 PNG,按附录 A 抽取后产出的文档**必然**满足上表全部上界。逐项论证:

**文档字节必须按分量累加,不能只按 `grid` 形态估。** 上一版只算了 `行内容 + 行开销 + 调色板 + 约 200`,那等价于假设整份文档是一条覆盖全图的 `grid`;但附录 A 在 ops 未超预算时输出的是 **`rect` / `grid` 混合序列**,而每个 `rect` 对象自身还有六个键的 JSON 开销。

反例(已实算):`3 × 65536` 的双色图,每行纯色、相邻行反色 —— 每行一条 `rect`,共 **65,536** 条。在**旧的** `OPS_CAP = 65,536` 下这恰好不触发回退,按规范形式序列化:仅 op 部分就 9,229,465 字节,整份文档 **9,229,714** 字节;而旧公式给出的"上界"是 1,769,656 字节,**反而比实际小 7,460,058**。一个被实际输出突破的"上界"不是上界。

注意:在当前 `OPS_CAP = 32,768` 下,同一个输入**会**触发回退,它已不是可构造的反例。保留这段是为了记下**证明方法的错误**——旧公式按"整图一条 `grid`"估算,漏掉了每个 op 对象自身的 JSON 开销。只要 ops 未超预算,规范输出就是 `rect`/`grid` 混合序列,这个漏项与 `OPS_CAP` 取多少无关,所以证明必须按分量做。

正确的估算是分量式的;各分量互不重叠地覆盖字节,相加即得保守上界:

```
固定结构      <= 1,024                                    // 键名、括号、缩进、结尾
调色板        <= 65,535 x 16              =  1,048,560    // 每项 缩进4+引号2+8位+逗号1+换行1
op 对象       <= OPS_CAP x 200            =  6,553,600    // 单个 rect 规范形式约 141 字节,取 200 保守
grid 内容     <= 4 x area                 = 16,777,216    // tw <= 4
grid 行开销   <= 32 x H <= 32 x 65,536    =  2,097,152    // 实测每行 16(缩进12+引号2+逗号1+换行1),取 32 保守
                                            -----------
合计                                        = 26,477,552  <  67,108,864
面积          <= 2^22                                     // 由 §8.1 输入接受集保证
ops           <= OPS_CAP = 32,768                         // 由附录 A 第 8 步全局回退保证
H             <= 65,536                                   // 由 §5.0.1 的 height 上界保证
```

几个说明:

- **`OPS_CAP` 取 32,768 是保守设计选择,不是被界逼出来的。** 按上面的分量式:`OPS_CAP = 65,536` 时合计 33,031,152(余量 **50.78%**),`32,768` 时合计 26,477,552(余量 **60.55%**)——两者都远低于 64 MiB。保留 32,768 的理由只有两条:真实素材最大约用到 2,730 条 `rect`(16 × 512),32,768 已是 12 倍余量;以及不必为一个已经宽松的界去改四处数字。
- 上一版曾以"余量太薄"为由把 `OPS_CAP` 从 65,536 降到 32,768。**那个理由已失效**:它依据的百分比出自下面要说明的、已被本节推翻的旧公式。此处不再复述那些数字——复述只会让后来者误以为它们仍是结论。
- **各分量相加是保守的**:`grid` 内容与 `rect` 覆盖的像素不可能同时占满 `area`,这里把两者都按满额计入。
- **`grid` 行开销按 `32 × H` 计**,`H` 的上界来自 §5.0.1 而非 `area`:行数受 `height <= 65,536` 约束,与面积无关。
- **这一版修正了 `grid` 行开销的两处错误,而两处方向相反**(上一版把方向相反的两个偏差当成同一个方向的偏差,这是它判断失误的根源之一):
  - ① **每行开销低估**:按顶层缩进 4 写成 8 字节;`grid` 的行实际嵌套在 `layers[0].ops[i].grid` 下,缩进是 **12**,非末行开销为 12 + 引号 2 + 逗号 1 + 换行 1 = **16**。这一项把合计**算小**。
  - ② **行数上界过度宽松**:写成 `H <= area`(= 4,194,304),而 §5.0.1 早已把 `height` 限在 **65,536**。这一项把合计**算大 64 倍**。
  - 净效果由 ② 主导:旧的行开销项是 8 × 4,194,304 = 33,554,432,按实际约束应为 16 × 65,536 = 1,048,576(采用 32 字节/行保守计为 2,097,152),前者是后者的 16 至 32 倍。所以上一版合计 57,934,832 是**虚高**的,并由此得出"余量只剩几个百分点"的错误结论。改正后合计 26,477,552,余量 60.55%。
- 按 **32** 字节/行而非实测的 16 计,是给序列化层级留一级余量:若将来 op 再嵌一层,缩进增加而本表不必重算。
- 若把面积放到 2^24,同一分量式给出约 **76,809,200** 字节(73 MiB),**仍超** 64 MiB——结论不变,面积仍须收到 2^22。
- **防腐条款**:上表每一项都对应一个"会改变字节量"的规范要素。**给任何 op 增删成员、新增 op 类型、改动 §3.7 的序列化规则、或改动面积/`OPS_CAP` 上界,都必须重算本表**,否则这个证明会像前两版那样悄悄失效:再前一版"漏了一项"(每个 op 对象的 JSON 开销),上一版则是**两个方向相反的量各自算错**。两次都不是算术失误,而是**证明所依据的模型与真实序列化不符**。

- 文档侧越界一律报 `PXL002`(§11 阶段 6);输入 PNG 侧越界报 `PXL006`(§8.3)。
  **例外:文档 UTF-8 字节数这条必须在 JSON 解析之前判。** 67,129,581 字节的文档在
  -Xmx128m / 256m / 512m 下都会**在解析阶段**OOM,先解析再判等于没有上限。因此
  `PxlParser` 必须先看 `byte[].length`,CLI 必须先看 `Files.size`;这条的优先级高于阶段 2/3 的
  UTF-8 与 JSON 语法错误——超限文档报 `PXL002`,不报 `PXL001`。
- **资源语义**:在上述**全部**上界之内,一个符合规范的实现**必须**能处理;实现内存不够是它不符合规范,不是 conformance 的例外,也不许以静默降级(跳过着色、只画前若干层)应付。

> 与 AGENTS.md §8 的 O2 不冲突:O2 的「大图允许但警告、不设硬阈值」针对抽取器的**警告策略与体积统计**,不是格式合法性。2^22 像素仍比真实素材(最大 16 × 512 = 8192 像素)高三个数量级。**已作为落地假设固定**,依据与推翻代价见附录 C.3 的 C-7。

### Core §5.1 `fill`

**参数**:`slot`(integer)。无坐标参数。

**语义**:把当前图层的**全部** `width` × `height` 个像素设为 `slot`。等价于 `rect(0,0,width,height,slot)`。

**边界/越界**:无坐标,不涉及裁剪。

**像素精确保证**:整层每个像素都等于该 slot 的 texel 值,零例外。

### Core §5.2 `rect`

**参数**:`x`、`y`、`w`、`h`、`slot`(均 integer)。

**语义**:在 `x <= px < x+w` 且 `y <= py < y+h` 上写入 `slot`。**右开区间**:从 `x` 起算 `w` 个像素,`x+w` 那个像素不属于本矩形。

**越界**:按 §5.0 裁剪。

**像素精确保证**:覆盖集恰好是上述整数格点集,不多一个像素,不少一个像素。

### Core §5.3 `pixel`

**参数**:`x`、`y`、`slot`。

**语义**:只写 `(x,y)` 一个像素。等价于 `rect(x,y,1,1,slot)`。

**越界**:裁剪(即空操作)。

### Core §5.4 `line`

**参数**:`x0`、`y0`、`x1`、`y1`、`slot`(均 integer)。

**语义**:画一条**含两端点**的 Bresenham 直线。为避免"Bresenham"在实现间产生不同像素集,算法被**逐字符固定**如下,实现必须给出与之逐像素相同的结果:

```
dx = |x1 - x0|;  sx = (x0 < x1) ? 1 : -1
dy = -|y1 - y0|; sy = (y0 < y1) ? 1 : -1
err = dx + dy
x = x0; y = y0
循环:
  写入 (x, y)
  若 x == x1 且 y == y1:结束
  e2 = 2 * err
  若 e2 >= dy: err = err + dy; x = x + sx
  若 e2 <= dx: err = err + dx; y = y + sy
```

两个"若"**各自独立判断**,同一轮可能同时成立(此时同时走 `x` 与 `y`,即对角步进)。全程只做整数加、减、比较、绝对值和乘 2。

**不做端点交换归一**:同一对端点按相反方向画(`line(a,b)` 与 `line(b,a)`)在部分斜率下**给出不同的像素集**(实测 `(2,6)->(10,5)` 与反向点数相同但点集不同)。这不是缺陷,是上式逐字固定的必然结果。实现**不得**为了"对称"而交换端点、翻转符号或换用另一套 Bresenham 变体——那会改变像素,并让两个实现分叉。

**像素精确保证**:

- 两端点必被写入,且是集合中的第一个与最后一个像素。
- 生成的是 8-连通路径:相邻两像素的 `x`、`y` 差各不超过 1。
- `x0 == x1` 且 `y0 == y1` 时只写 1 个像素。
- 水平/垂直线不会产生锯齿偏移。

**越界**:逐点裁剪;线段可被画布切成多段,不报错。

### Core §5.5 `grid`

**参数**:`x`、`y`(integer,落笔原点)、`grid`(token 行数组,格式见 §3.4)。

**语义**:把 `grid` 的第 `j` 行、第 `i` 段 token 解码成 slot,写入 `(x+i, y+j)`。这是像素级的**逐点覆盖**形式,也是"逐像素版"的基准。

**边界**:`grid` 自身的尺寸由行数与行长决定(§3.4 保证两者都 ≥ 1,故尺寸恒 ≥ 1×1),**不要求**等于 `width` × `height`;小于画布时是局部补丁。

**越界**:逐点裁剪。于是一份 `grid` 可以大于画布,超出部分被丢弃而不报错。

**像素精确保证**:解码出的 slot 与写入位置一一对应,不重排、不缩放。

### Core §5.6 `mirror`

**参数**:`from`(对象 `{x,y,w,h}`)、`to`(对象 `{x,y}`)、可选 `flipX`、`flipY`(boolean,默认 `false`)。

**语义**:把 `from` 矩形内的**已绘内容**翻转后写到以 `to` 为左上角的等尺寸矩形。翻转标志与 `stamp` **同名同义**,不另设 `axis` 之类的第二套词——同一个概念在全文只用一个字段名。否则实现方按字面把 `axis: "x"` 读成"绕 x 轴翻转"(即上下),就能得到一个同样自洽、但像素不同的渲染器。

- `flipX` 为真:水平翻转(左右镜像)。源像素 `(fx+w-1-i, fy+j)` 写到 `(to.x+i, to.y+j)`。
- `flipY` 为真:垂直翻转(上下镜像)。源像素 `(fx+i, fy+h-1-j)` 写到 `(to.x+i, to.y+j)`。
- 两者同真:先 X 后 Y,等价于 180 度旋转。两者皆假:纯拷贝。

其中 `fx = from.x`,`fy = from.y`,`0 <= i < w`,`0 <= j < h`。

**快照语义(重要)**:源区域必须在**任何写入发生前**整体读出为快照,再从快照写到目标。因此 `from` 与目标区域重叠时结果仍然唯一确定,与实现无关。没有这一条,"镜像"就会依赖写入顺序。

**像素精确保证**:只做整数索引重排,不插值,不产生新颜色。镜像后的像素集合与源像素集合**逐值相同**,只是位置重排。

**越界**:读取侧**不裁剪**——`from` 落在图层之外的像素按**透明 slot 0** 参与快照,因此会向目标写出 `0`;写入侧按 §5.0 裁剪。

这一条必须钉死:若改成"越界源像素跳过、目标保持不动",同一份文档会渲染出不同像素,而两种读法在文字上都讲得通。按本节定义,`mirror` 是**全函数**:任何 `w`/`h` 与画布的重叠方式都有唯一结果。

### Core §5.7 `erase`

**参数**:`x`、`y`、`w`、`h`。

**语义**:把该矩形设为**透明 slot 0**,即 texel 值 `00000000`。等价于 `rect(x,y,w,h,slot=0)`。

注意:`erase` 清的是**当前图层**的这些像素,并不删除 op、不改变调色板、不影响其它图层。

**越界**:裁剪。

### Core §5.8 `stamp`

**参数**:`sprite`(string,引用 `sprites` 中的名字)、`x`、`y`、可选 `flipX`、`flipY`(boolean,默认 `false`)。

**语义**:把命名 sprite 的 token 矩形(§3.4 保证尺寸恒 ≥ 1×1)解码后写到以 `(x,y)` 为左上角的位置。若 `flipX` 为真,先水平翻转;若 `flipY` 为真,再垂直翻转(先 X 后 Y;两者互不交换,同真时等价于 180 度旋转)。

sprite 的 slot 值取自**同一份** `palette`,与 `encoding` 共用同一 token 宽度。

**引用不存在**:`PXL005`。sprite 自身**不**参与合成:定义但从未被 `stamp` 引用的 sprite 对输出没有影响。

**像素精确保证**:与 `grid` 相同,只是允许翻转。

**越界**:逐点裁剪。

## Core §6. 图层与合成

### Core §6.1 顺序

从 `layers[0]`(最底)到 `layers[n-1]`(最顶)依次合成。累加器初值是一块 `width` × `height`、每像素 `00000000` 的缓冲。

每个图层先在自己的一块全透明缓冲上依序执行 `ops` 得到该层像素,再按 `blend` 合到累加器上。**同一图层内的 op 不混合**(§5.0)。

### Core §6.2 整数取整约定

颜色运算**全整数**,禁止浮点参与颜色计算(包括单双精度浮点、任何小数中间量、任何对非整值取整)。唯一定义:

```
div255(v) = (v + 127) / 255        // 整数除法,向零取整;要求 0 <= v <= 65025
```

记号:累加器像素 `(dr,dg,db,da)`,当前层像素 `(sr,sg,sb,sa)`,单通道记作 `c` 属于 {r, g, b}。

### Core §6.3 `normal`

```
t    = 255 - sa
aNum = sa * 255 + da * t               // 未取整的 alpha 分子,范围 0..65025
ao   = (aNum + 127) / 255              // 即 div255(aNum),也就是 outA
若 aNum == 0:
    若 (sr,sg,sb,sa) == (0,0,0,0):                        // 源是透明 slot,没有颜色可给
        out = (dr, dg, db, 0)                             // 保留下层 RGB
    否则:
        out = (sr, sg, sb, 0)                             // 保留上层 RGB(§7)
否则:
    half = aNum / 2                                       // 整数除法
    outc = (sc * sa * 255 + dc * da * t + half) / aNum    // 整数除法
    out  = (outr, outg, outb, ao)
```

**为什么用 `aNum` 而不是先算出取整后的 `ao`。** 只有用**未取整**的 `aNum` 同时充当 RGB 的分母与 alpha 的分子,通道上界才成立:

```
cNum = sc * sa * 255 + dc * da * t
     <= 255 * sa * 255 + 255 * da * t        // 因为 sc、dc 都 <= 255
     =  255 * aNum
故 outc = (cNum + aNum/2) / aNum <= (255*aNum + aNum/2) / aNum = 255
```

所以 `outc` 恒在 0..255,**永远不需要钳位**。反过来说,若先算 `ao` 再用 `den = ao * 255` 当归一化分母,上界就掉了:源 `FFFFFF01`、目标 `FFFFFF80` 时 `ao` 被向下取整成 128(真值 128.498),分母偏小,通道算出 **256**——一个 RGBA8 表达不了的值,实现只能自行钳位、截断或报错,而规范没写该选哪个。这不是补一条钳位规则能修的:钳位会让边界像素与 `ao` 互相矛盾,换一组输入还会再错。

**分支条件**:`aNum > 0` 时必有 `aNum >= 255`(因 `sa > 0` 或 `da > 0`),故 `ao >= 1`。所以 `aNum == 0`、`ao == 0`、`sa == 0 且 da == 0` 三者等价,下面这条分支的触发条件没有歧义。

`aNum == 0` 分支的存在理由:此时上下两层都没有**可见**内容,于是 RGB 必须由两者之一保留下来,规则是**谁拥有颜色就留谁的**:

- 源是透明 slot(`00000000`)——它没有颜色——则保留下层 RGB。否则一个空图层(`ops` 为空数组、或一条 `fill slot 0`)会把下层整张 `FFFFFF00` 图抹成 `00000000`。
- 源不是透明 slot(例如 `FFFFFF00`)——它有自己的颜色——则保留上层 RGB。否则一张"全 `FFFFFF00`"的单图层图回渲会变成"全 `00000000`",像素等价直接破裂。

两个分支都不是可选的:去掉前者会毁掉多层文档,去掉后者会毁掉真实语料里占绝大多数的单层文件(见附录 C)。

### Core §6.4 `multiply`

```
mc   = div255(sc * dc)                 // 先逐通道相乘
t    = 255 - sa
aNum = sa * 255 + da * t
ao   = (aNum + 127) / 255
若 aNum == 0:
    若 (sr,sg,sb,sa) == (0,0,0,0):                        // 源是透明 slot,没有颜色可给
        out = (dr, dg, db, 0)                             // 保留下层 RGB
    否则:
        out = (sr, sg, sb, 0)                             // 保留上层源 RGB(§7)
否则:
    half = aNum / 2
    outc = (mc * sa * 255 + dc * da * t + half) / aNum
    out  = (outr, outg, outb, ao)
```

即:先把源色乘进目标色得到 `mc`,再用与 `normal` **完全相同**的公式合成,包括 §6.3 的 `aNum` 归一与同一条上界证明(把 `sc` 换成 `mc` 即可,`mc <= 255` 仍成立,故 `outc <= 255`)。`aNum == 0` 分支与 §6.3 逐条同构:源为透明 slot 时保留下层 RGB,否则取 `sr/sg/sb`(原源色,而非 `mc`)——底下没有任何东西可乘,源像素应当原样透过。

### Core §6.5 `mask`

```
若 (sr,sg,sb,sa) == (0,0,0,0):              // 源是透明 slot
    out = (dr, dg, db, da)                  // 下层完全不变
否则:
    out = (dr, dg, db, div255(da * sa))     // 只乘 alpha,RGB 原样保留
```

`mask` 是**透明度模板**:它只能压低 alpha,既不产生颜色,也不丢弃下层的 RGB。因此它可以造出"RGB 非零且 alpha = 0"的像素,而这种像素**必须**被当作真实像素保留(§7)。

### Core §6.6 七个已算出的结果(含三个 alpha = 128 的混合)

以下结果由 §6.2–6.5 的公式逐位计算得出,是 conformance 用例的期望值。

**(a) `normal`**:源 `FF000080`(红,alpha 128)合成到 `0000FFFF`(不透明蓝)。

```
sa=128, t=127, da=255
ao = 128 + div255(255*127 = 32385) = 128 + 127 = 255
den = 65025, half = 32512
r: (255*128*255 +   0*255*127 + 32512) / 65025 = 8355712 / 65025 = 128
g: (  0*128*255 +   0*255*127 + 32512) / 65025 =   32512 / 65025 =   0
b: (  0*128*255 + 255*255*127 + 32512) / 65025 = 8290687 / 65025 = 127
结果 = 80007FFF
```

注意 r + b = 128 + 127 = 255:不是"各半"的对称取整,而是上面这一条唯一确定的整数结果。实现不得换用"把 127.5 就近取整"之类另一套规则。

**(b) `multiply`**:源 `80FF0080` 合成到 `112233FF`。

```
mr = div255(128*17 = 2176) = 9
mg = div255(255*34 = 8670) = 34
mb = div255(  0*51 =    0) = 0
sa=128, t=127, da=255, ao=255, den=65025, half=32512
r: (  9*128*255 + 17*255*127 + 32512) / 65025 =  876817 / 65025 = 13
g: ( 34*128*255 + 34*255*127 + 32512) / 65025 = 2243362 / 65025 = 34
b: (  0*128*255 + 51*255*127 + 32512) / 65025 = 1684147 / 65025 = 25
结果 = 0D2219FF
```

**(c) `mask`**:源 `00FF0080` 合成到 `112233FF`。

```
out = (0x11, 0x22, 0x33, div255(255*128 = 32640) = 128)
结果 = 11223380
```

**(d) `mask` 造出 alpha = 0 而 RGB 非零**:源 `00FF0000` 合成到 `112233FF`。

源不是透明 slot(它不是 `00000000`),故走第二个分支:

```
out = (0x11, 0x22, 0x33, div255(255*0 = 0) = 0)
结果 = 11223300
```

这个结果**不得**被折叠成 `00000000`。

**(e) 透明 slot 不吞掉下层的不可见颜色**:源 `00000000` 合成到 `FFFFFF00`。

```
ao = 0 + div255(0 * 255) = 0
源是透明 slot -> out = (dr, dg, db, 0) = (0xFF, 0xFF, 0xFF, 0) = FFFFFF00
结果 = FFFFFF00        // 恒等,下层完好
```

**(f) 不可见颜色只在"底下什么都没有"时透过**:源 `FFFFFF00` 合成到 `00000000`。

```
ao = 0 + div255(0 * 255) = 0
源不是透明 slot -> out = (sr, sg, sb, 0) = (0xFF, 0xFF, 0xFF, 0) = FFFFFF00
结果 = FFFFFF00
```

这正是单图层 `FFFFFF00` 全图能逐字节回渲成自己的原因,也是 §7 第 2 条的算术落点。

**(g) 上界钳位的反例(必须有用例钉住)**:源 `FFFFFF01` 合成到 `FFFFFF80`。

```
sa=1, t=254, da=128
aNum = 1*255 + 128*254 = 255 + 32512 = 32767
ao   = (32767 + 127) / 255 = 128
half = 16383
r    = (255*1*255 + 255*128*254 + 16383) / 32767 = 8371968 / 32767 = 255
结果 = FFFFFF80
```

用先取整 `ao` 的旧写法会得到通道 **256**。**但这一例本身看不出钳位**:把 256 钳到 255 恰好等于正确结果 `FF`,"旧公式 + 钳位"能通过它。要真正区分,需要"正确值 < 255 而旧公式给出更大值"的输入——见语料 `blend-formula-818181-normal`(源 `81818101` over 目标 `81818180`:正确 `81818180`,旧公式 `82828280`)与 `blend-formula-818181-multiply`。白例钉"旧公式会产出域外值",818181 例钉"旧公式即使不越界也错",两条合起来才兑现"不许靠钳位补救"。

### Core §6.7 可测的不变量

以下六条都必须有用例钉住;它们也划清了"哪些差异是缺陷、哪些只是 `multiply` 的定义"。

1. **单图层 `normal` 恒等**:单图层、`blend: "normal"` 的文档,回渲结果必须**逐像素等于**其 op 所写的像素,原位不变(含 `FFFFFF00` 这类不可见颜色)。对 9 个代表色逐一验证成立。这是 §6.3 `ao == 0` 分支与 `normal` 公式精确性的直接推论(§6.6f)。
2. **透明 slot 恒等**:透明 slot 像素(`00000000`)在三种 `blend` 下都**完全恒等**,下层像素四通道一个字节都不变。`normal` / `multiply` 由 §6.3 / §6.4 的透明源分支保证,`mask` 由 §6.5 第一个分支直接返回(§6.6e)。
3. **`normal` 下全不透明覆盖**:`sa = 255` 时结果恒等于上层源值,且 `ao = 255`。
4. **`multiply` 不是"覆盖"**:它的结果是 `div255(sc * dc)` 再按 alpha 合成,所以**不能当底层**——下层为空时 `dc = 0`、`mc = 0`,任何不透明源都会得到 `000000FF`(乘成黑)。这是 `multiply` 的定义,不是缺陷;实现方**不得**为此加特例。同理,`mask` 下"全不透明覆盖"也不成立:它的 RGB 恒等于下层。
5. **`mask` 从不改 RGB**:`mask` 只乘 alpha,RGB 恒取下层;因此它既能造出 `A = 0` 而 RGB 非零的像素(§6.6d),也必须把这种像素原样交出去。
6. **不可见颜色(`RGB` 非零且 `A = 0`)的行为必须按 `blend` 分别陈述**,不能一概而论:
   - `normal` / `multiply`:下层可见时**不**改变下层;下层为空时**保留自己的 RGB**(§6.3 / §6.4 的 `aNum == 0` 分支)。
   - `mask`:它本来**就是**用来改下层 alpha 的。实测 `11223300` mask 到 `445566FF` 得 `44556600`——**下层 alpha 被改掉了**;而当 `mask` 层作底层(下层为空)时得 `00000000`,**不保留源 RGB**。
   - 因此旧版那句「任何图层序列都不会凭空增删 RGB 字节」**只对 `normal` / `multiply` 成立**。含 `mask` 的文档里,alpha 可以被 mask 归零而 RGB 原样留下——那正是 §7 第 2 条要的形态,不是缺陷。

## Core §7. 透明度语义

本节是 AGENTS.md §3.5 硬约束的形式化,优先级高于任何"顺手简化":

1. **只有 texel 值精确等于 `00000000` 的像素**归入透明 slot 0。判等是四通道全零,不按 alpha 单独判断。
2. **RGB 非零且 alpha = 0 的像素**(例如 `FFFFFF00`、`11223300`)是**普通像素**:它占一个自己的 slot、有自己的 token、进调色板、按 §4.4 参与首次出现顺序分配。
3. 合成时,**不得**把这类像素当作"没有像素"丢弃。具体地:
   - `normal` / `multiply` 在上下两层都不可见(`aNum == 0`)时,RGB 按「有颜色者胜;两者都有颜色时上层胜」传播,与 §6.3 / §6.4 的公式逐字对应:
     - 上层是**透明 slot**(`00000000`,没有颜色)→ 保留**下层** RGB;
     - 上层是**有颜色的不可见像素** → 保留**上层** RGB。这与单图层恒等一致:只含这类像素的图层叠在空累加器上必须原样返回(§6.6f);
     - 因此**两层是不同颜色的不可见像素时取上层**:下层 `FFFFFF00`、上层 `FF000000` → 结果 `FF000000`,不是 `FFFFFF00`。这句必须明写,否则本节的散文会与公式矛盾。
   - `mask` 不得清除下层的 RGB(§6.5)。
   - 渲染器写 PNG 时,必须原样写出这四个字节。
4. **不得**在抽取或渲染的任何一步按"alpha 是否为 0"做透明化归一;也不得把 alpha = 0 的像素的 RGB 清零、丢弃或合并到透明 slot。

**判定方式**:一张 `FFFFFF00` 全图的位图,抽取后 `palette` 长度必须为 1(而非 0),回渲必须逐字节得到全 `FFFFFF00`(而非全 `00000000`)。真实语料中该类文件有 3045 个(附录 C)。

## Core §8. 位深与拒绝策略

输入位图是 PNG。current core 的**接受集是封闭且穷举的**:下表之外的一律拒绝,不给实现留"自行选择"的余地。

### Core §8.1 接受集

| 项目 | 接受 | 说明 |
|---|---|---|
| 样本深度 | **仅 8** | 1 / 2 / 4 / 16 一律拒绝(§8.3) |
| 交错 | **仅 0**(非交错) | Adam7 拒绝 |
| `width` / `height` | **1..65536**,且 `width × height <= 2^22` | 超出即输入不合法,报 `PXL006`(§8.3)——不是"实现内存不够"。上界见 §5.0.1 / §5.0.2 |
| 色彩类型 0(灰度) | 接受 | `tRNS` 可选,语义见 §8.5 |
| 色彩类型 2(RGB) | 接受 | `tRNS` 可选,语义见 §8.5 |
| 色彩类型 3(索引) | 接受 | 需 `PLTE`;`tRNS` 可选 |
| 色彩类型 4(灰度 + alpha) | 接受 | 不得有 `PLTE` 或 `tRNS` |
| 色彩类型 6(RGBA) | 接受 | `PLTE` 可有但忽略;不得有 `tRNS` |
| 其它色彩类型 | 拒绝 | 非法或未定义 |
| `pHYs` / `tIME` / `bKGD` / `iCCP` / `tEXt` / `zTXt` 等 ancillary chunk | 接受并**忽略** | 不参与像素,不得因其存在而报错(AGENTS.md §4.2 的动机) |

### Core §8.2 到 RGBA8 的精确转换

| 色彩类型 | R | G | B | A |
|---|---|---|---|---|
| 0,无 `tRNS` | 样本 | 样本 | 样本 | 255 |
| 0,有 `tRNS` | 样本 | 样本 | 样本 | 样本 == `tRNS` 灰度值 ? 0 : 255 |
| 2,无 `tRNS` | 样本 0 | 样本 1 | 样本 2 | 255 |
| 2,有 `tRNS` | 样本 0 | 样本 1 | 样本 2 | `(r,g,b)` 命中 `tRNS` ? 0 : 255 |
| 3,有 `tRNS` | `PLTE[3i]` | `PLTE[3i+1]` | `PLTE[3i+2]` | `tRNS[i]`;`i >= tRNS 长度` 时为 255 |
| 3,无 `tRNS` | `PLTE[3i]` | `PLTE[3i+1]` | `PLTE[3i+2]` | 255 |
| 4 | 样本 0 | 样本 0 | 样本 0 | 样本 1 |
| 6 | 样本 0 | 样本 1 | 样本 2 | 样本 3 |

不做任何色彩空间变换:颜色按字节搬运,`iCCP` 不解释(§10)。

### Core §8.3 拒绝(`PXL006`)

必须**显式拒绝**并报 `PXL006`,且**不得**静默降位深或静默转换:

- 样本深度 **16** —— 任何降位都有损,违反 §1 的无损前提;
- 样本深度 **1 / 2 / 4** —— 这是有意的**范围收窄**:这些形态(尤其 4 bit 索引 PNG)本可无损展开,但 current core 不展开,以换取"接受集小而封闭";
- **交错**(Adam7);
- 8.1 之外的色彩类型;
- **`width` 或 `height` 超过 65536** —— PXL 画布上界就是 65536(§5.0.1);这样的 PNG 无论怎么抽都写不出合法 PXL,必须在**输入侧**拒绝,而不是等抽取完再撞上 `PXL002`;
- **`width × height` 超过 §5.0.2 的面积上界** —— 同上,是文档层面不合法,不是"这台机器内存不够";
- 结构损坏到拿不到像素的 PNG(签名 / IHDR / IDAT 缺失,或校验不通过)。

拒绝必须发生在**产出任何 PXL 之前**:不得先写出半份文件再报错。16 bit 与低位深展开列为 v1 候选(§12),current core 不做。

### Core §8.4 实测覆盖与未覆盖面

实测语料 655 个文件(附录 C)只出现样本深度 8、非交错、色彩类型 **2 与 6**。因此 8.1 里的色彩类型 **0 / 3 / 4 尚无真实素材覆盖**:它们靠合成正负例负责,不得因为"没见过"就从接受集里删掉,也不得因为"写进规范了"就声称已验证。

### Core §8.5 PNG 解码的封闭规则

自己写解码器时,下面每一条都会让两个实现分叉,必须钉死。违反其中任何一条即 `PXL006`。

**校验与 chunk 结构**

- 文件前 8 字节必须**恰好**是 `89 50 4E 47 0D 0A 1A 0A`(PNG 签名)。
- **每一个 chunk 的 CRC 都必须校验**,包括 IHDR、PLTE、tRNS、IDAT 与 **IEND**;任何一个不通过即拒绝。凡是"要不要校验某个 chunk"需要逐类型列举的写法,本身就说明规则没封闭——所以这里一律校验,不枚举。
- **chunk 类型名必须恰为 4 个 ASCII 字母**(`A`–`Z`、`a`–`z`)。出现数字、标点、空格或非 ASCII 字节即拒绝。**第三个字节的保留位必须为 0**(即必须是大写字母),否则拒绝——这既是 PNG 规范的要求,也让"首字母大小写区分 critical / ancillary"这个判据有定义;不钉住它,类型名里混进一个数字就没人说得出一串 chunk 该怎么归类。
- **长度读取必须防溢出**:chunk 长度按 **32 位无符号**读,必须满足 `len <= 2,147,483,647` 且 `8 + len + 4 <= 文件剩余字节数`;任一不满足即拒绝。这些和必须用 64 位或等价的宽整型计算,**不得依赖宿主语言的整型回绕**。
- **不得把"长度超出文件末尾"当成"读到文件结束"**——那会把截断的文件静默当成合法;`IEND` 缺失同样按拒绝处理。
- IHDR 必须**恰好一个**且排在第一位;IEND 必须**恰好一个**且排在最后。
- **IHDR 的 chunk 数据长度必须恰为 13 字节**;**压缩方法必须为 0**;**过滤方法必须为 0**。
- **IEND 的 chunk 数据长度必须为 0**。
- **`IEND` 之后不得有任何字节**——多余数据不得静默忽略。
- **`PLTE` 若存在必须早于第一个 `IDAT`**;**`tRNS` 必须早于第一个 `IDAT`**,并且**存在 `PLTE` 时必须晚于 `PLTE`**(`IHDR → tRNS → PLTE → IDAT` 这种顺序非法)。这条此前没写,于是一张 `IHDR → IDAT → PLTE → IEND` 的索引图 CRC 全对却无人拒绝,而"先收全文件再解码"与"流式解码"会得到不同结果。
- **IDAT 必须连续出现**(中间不得夹其它 chunk),可多块,按出现顺序拼接。
- **重复约束必须按"这个 chunk 是否被读取"分两类**,不能对所有非 IDAT 块一刀切:
  - **会被读取的**:`IHDR`、`PLTE`、`tRNS` 各自**至多一个**,多一个即拒绝;`IDAT` 例外,可多块但必须连续。
  - **不被读取的**(全部 ancillary:`tEXt` / `zTXt` / `iTXt` / `pHYs` / `tIME` / `bKGD` / `iCCP` / `gAMA` / `sRGB` … 以及未知 ancillary):**出现任意次都接受,内容一律忽略**。

  为什么后者不能按"重复即拒绝"处理:PNG 规范本身允许 `tEXt` / `zTXt` / `iTXt` 多次出现、关键词也可重复。于是两张**像素完全相同**的合法图,可能一张带一条 `tEXt`、另一张带两条;若一刀切,前者通过、后者被拒,而它们的像素一模一样——这种拒绝找不到任何像素层面的理由。

  未知 **critical** chunk 仍然拒绝,但那与"重复"无关(见下一条)。
- 未知 **critical** chunk(类型名首字母大写)即拒绝;未知 **ancillary** chunk(首字母小写)**忽略其内容**,重复出现同样接受(见上一条)。
- `width` 或 `height` 为 0 即拒绝;超过 65536 或面积超过 §5.0.2 上界也拒绝(§8.3)。

**PLTE / tRNS**

- 色彩类型 3 **必须**有 `PLTE`;色彩类型 0 / 4 **不得**有 `PLTE`;色彩类型 2 / 6 允许有但**忽略**。
- `PLTE` 长度必须是 3 的倍数、项数 1..256,否则拒绝。
- 色彩类型 3 的样本索引 **>= PLTE 项数** 即拒绝(不钳位、不环绕)。
- `tRNS` 长度:色彩类型 3 时不得超过 PLTE 项数;色彩类型 0 时**必须恰为 2 字节**;色彩类型 2 时**必须恰为 6 字节**;色彩类型 4 / 6 出现 `tRNS` 即拒绝。
- 色彩类型 **0 / 2 的 `tRNS` 语义务必钉死**(current core 明确支持,不拒绝):`tRNS` 的值按**大端**读出,与样本逐字节比较——命中则该像素 alpha = 0,**RGB 原样保留**;未命中 alpha = 255。于是这两类输入也能产出 §7 关心的"RGB 非零而 A = 0"像素,语义与色彩类型 3 的 `tRNS` 一致。
  - **比较前必须按样本深度掩掉高位。** PNG 规范(PNG 第三版 §11.3.2.1)规定:位深不足 16 时,`tRNS` 里只有低 `depth` 位有效,其余位不参与比较。因此样本深度 8 时 `tRNS = 0x0180` **命中**样本 `0x80`(`0x0180 & 0xFF = 0x80`)。两种读法("整值比"与"掩码后比")在文字上都讲得通,而只有后者与 PNG 一致;早前本规范写的是"按 16 位整值比较",那是**错的**,已更正。

**IDAT 解压与行解码**

- 拼接后的 IDAT 必须是**恰好一个完整 zlib 流**:zlib 头合法、正常收尾、**Adler-32 必须校验**。流提前结束、流后有剩余字节、或出现第二个 zlib 流,都拒绝。
- 解压后的字节数必须**恰好**等于 `height × (1 + width × 每像素字节数)`;多一个或少一个都拒绝,不得补零、不得截断、不得只取前若干行。
- 每行的过滤器字节必须是 0..4;其它值拒绝。
- 行过滤器按 PNG 规范逐字节还原,不得跳过任何一行。
- 结尾若还有多余 chunk 或多余字节,按上面的 chunk 规则处理(不静默忽略)。

## Core §9. 确定性

同输入必须给出逐字节相同的输出。因此:

- **禁止随机**:不得使用任何随机源、任何未固定种子的伪随机序列。
- **禁止时钟**:不得读写当前时间、时间戳、时区、进程耗时等任何非输入量。输出不得含任何时间信息。
- **禁止 locale**:不得依赖区域设置。大小写转换、数字格式化、排序比较都必须与 locale 无关;十六进制字母固定大写;数值一律十进制整数。
- **禁止依赖文件系统遍历顺序**:当一次调用处理多个文件时,处理顺序必须由显式排序(按路径字节序)确定,不得依赖目录枚举返回顺序。输出内容本身不得包含路径以外的环境信息。
- **禁止依赖哈希表迭代顺序**:调色板顺序由 §4.4 的扫描顺序决定,不得由容器迭代顺序决定。
- 禁止浮点参与颜色计算(§6.2)。
- 抽取器输出的字段顺序、缩进、换行必须逐字符合 §3.1,使"同图两跑零 diff"与"两实现零 diff"都成立。

**判定方式**(三层,强度不同):

- **抽取器**:同一输入连跑两次,`.pxl` 输出逐字节相同。
- **渲染器(同一实现内)**:同一文档连跑两次,产出的 **PNG 文件逐字节相同**——不只是像素相同。这条是强要求但可满足:§10 已把过滤器与 chunk 集合钉死,只需实现的 deflate 参数在同一实现内固定,不得依赖启发式、时钟或随机。
- **跨实现之间**:只要求**像素**相同(§10),不要求 PNG 字节相同。

旧版只写到像素相同,与本节开头"同输入必须给出逐字节相同的输出"以及 AGENTS.md §6 的「两次渲染字节相同」都不一致,已按上面三层改齐。

## Core §10. PNG 输出约定

本节是实现方要求,**不属于 PXL 格式本体**;换一个宿主库时这些约束可以变,但 current core 的实现必须满足,以便语料可复现。

- 输出 PNG:每通道 **8 bit**、色彩类型 **RGBA**(6)、**非交错**、无透明索引调色板。
- **行过滤器恒为 0**(None)。这让输出流不依赖压缩启发式,便于排查。
- 只写 **IHDR / IDAT / IEND** 三种 chunk 类型。**`IDAT` 允许分块,块数不限**(同一实现内两跑块数也必须相同,见 §9);除此之外不得写任何 chunk——特别地,`pHYs`、`tIME`、`bKGD`、`iCCP`、`tEXt`、`zTXt`、`gAMA` 等 ancillary chunk 一律不写。
- 本仓库不做色彩管理:颜色按字节搬运,不解释 `iCCP`。
- **同一实现、同一输入,两次写出的 PNG 必须字节相同**:压缩级别、块大小等 deflate 参数必须固定。这与跨实现只比像素并不冲突——前者约束一个实现的自洽,后者约束两个实现之间的一致性。

**跨语言只要求像素相同,不要求字节相同。** 这一条是规范的一部分,不是免责声明:

- 两个实现可以写出**不同的 PNG 字节**(不同压缩实现、不同 deflate 参数),这不算不一致。
- 一致性的判据是:两者解出的 **RGBA8 原始字节流**逐字节相同。判定方法见 §13.4。
- 同理,回渲产物与**原始素材**也只在像素层面比较:素材里原有的 `pHYs` / `tIME` / `bKGD` / `iCCP` 会被丢弃,文件 SHA-256 必然变化,这不是错误。

## Core §11. 错误分类

一套稳定错误码,两个实现**必须复用同一编号与同一触发条件**。错误文本可以不同,编号与触发条件不得不同。

| 码 | 名称 | 触发条件 |
|---|---|---|
| `PXL001` | 语法错 | 不是合法 JSON;**同一对象内成员名重复**(§3.2);未定义字段;缺少必需字段;JSON 类型类别不符(如 `width` 写成字符串、**`palette` 项不是字符串**);已知 op 的参数集合与 §5 不一致;`format` 不等于 `"PXL"`;`version` 不等于 0;`blend` 不在三值内;图层 `name` 不匹配 `[a-z][a-z0-9_-]*` 或在文档内重名;**`layers` 数组为空**(§3.2 要求至少 1 个图层);**`sprites` 的成员名不匹配同一条语法或在文档内重名**(§3.7);数组行不等长;**行数组为空、或某行为空串**(§3.4);行字符数不是 token 宽度的正整数倍;token 含 §4.2 / §4.3 枚举集之外的字符(含空格、制表符、**U+00A0**、控制字符;`char` 档用了 `z`、十六进制里出现小写字母也在此列)。**不符合 §3.7 规范形式不在此列**(§3.8) |
| `PXL002` | 尺寸 / 数值不符 | `width` / `height` 不是**整数值**的数(如 `1.5`;类型类别本身错属 `PXL001`)、或不在 1..65536;**已知 op 的** `x` / `y` / `x0` / `y0` / `x1` / `y1` / `w` / `h` / `slot` **不是整数值**、或越出 §5.0 的整数域(未知 op 的同名成员不查,见 `PXL004`);行数组的 token 数超过 65536(**是 token 数,不是字符数**,见 §3.4);**`width × height`、图层数、图层数 × 面积、每层 ops 数、sprites 个数、sprite 行数、文档字节数**任一超过 §5.0.2 的上界 |
| `PXL003` | 未知或不符的 encoding | `encoding` 不在 {`char`, `index`, `index4`};或该值虽在集合内但与 §4.5 由 `n` 派生的档位不一致 |
| `PXL004` | 未知 op | `op` 值不在八条图元之内。未知 op 的 **op 专属**成员(数值域、成员集合、形似 `grid` 的行数组、slot 引用)不检查,因此不会先报 `PXL002` / `PXL005`;**通用对象检查照常执行**(合法 JSON、成员名不重复、`op` 字段是否为字符串),所以重复键仍会先报 `PXL001`。详见 §11.1 的分界。已知 op 的参数集合检查归 `PXL001`,不归本码 |
| `PXL005` | 调色板 / slot 错 | `palette` 项**是字符串但不匹配** `^[0-9A-F]{8}$`(不是字符串属 `PXL001`,见那里);`palette` 含 `00000000`;`palette` 长度 >= 65536(§4.5 无档位可派生,见阶段 7 的说明);token 指向的 slot 大于 `palette` 长度;slot 超过该档上限;`stamp` 引用了不存在的 sprite |
| `PXL006` | **输入位图不受支持** | 样本深度不是 8;交错输入;不受支持的色彩类型(§8.1);`width` / `height` 超过 65536 或面积超 §5.0.2 上界;以及 §8.5 列出的全部 PNG 结构与校验拒绝项。该码在**解析 PXL 之前**产生,属输入侧。注意它**不**只管位深——名字保留历史,范围以本节为准 |

**`PXL001` 到底管不管取值**——旧版这里自相矛盾,现在按**管的种类**划分,两者不重叠:

- `PXL001` 管**结构 + 枚举 / 字面量合法性**:某个成员该不该出现、类型类别对不对、枚举取值是否在允许集合内(`format`、`version`、`blend`)、字面量拼写是否合法(token 字符、行空白、成员名格式、成员名重复)。
- **`op` 字段本身分两步判**,不要混:`op` **缺失或不是字符串** → `PXL001`(阶段 3,属结构);是字符串但**不在八条图元之内** → `PXL004`(阶段 8,属未知 op)。
- `PXL002` 管**数值域**:某个整数成员是否整数值、是否落在 §5.0 的区间内。

所以 `version = 1` 是枚举越界 → `PXL001`;`width = 1.5` 是数值域 → `PXL002`;`width = 1` 但 `x = 99999` 也是 `PXL002`。同一份文档不会同时命中这两类。

### Core §11.1 错误优先级

报错序是**阶段序**,不是错误码的大小序。有些检查依赖 `encoding`(token 宽度),而 `encoding` 是否合法本身要报 `PXL003`;若坚持一条扁平顺序,就会出现循环依赖——未知 `encoding` 配 `grid` 时,一边说先查 token 宽度(`PXL001`)、一边说 token 宽度未知要到 `PXL003` 才知道,两个实现必然分叉。因此 `PXL001` 分成前后两段,`PXL003` 夹在中间:

| 阶段 | 检查 | 码 |
|---|---|---|
| 1 | 输入位图(抽取侧):§8.1 / §8.5 全部接受与拒绝规则 | `PXL006` |
| 2 | 能按 UTF-8 解码(允许并忽略 BOM) | `PXL001` |
| 3 | 合法 JSON;成员集合;成员名不重复;类型类别;`format` 的值;`version`;`blend`;图层名;**`layers` 数组非空**(§3.2 要求至少 1 个图层);已知 op 的参数集合;**行数组非空、行元素非空串、同一数组内行长度相等**(这三项都不依赖 token 宽度,因此在 `encoding` 定值之前就能判定;行内字符是否合法依赖档位,归阶段 5) | `PXL001` |
| 4 | `encoding` 取值是否在 {`char`, `index`, `index4`} | `PXL003` |
| 5 | **依赖 token 宽度**的检查,**仅**这两项:行字符数是否为 token 宽度的正整数倍;**token 字符集**(含任何空白或控制字符一律非法,不引"空白字符"这个概念)。只针对**已知 `grid` op 的 `grid` 字段**与 `sprites` 的每个值 | `PXL001` |
| 6 | 数值域。**文档级**:`width` / `height` / 图层数 / 面积 / 每层 ops 计数 / `sprites` 项数 / sprite 行数 / 文档字节数(§5.0.1、§5.0.2 全部上界);**op 级**:已知 op 的 `x` / `y` / `x0` / `y0` / `x1` / `y1` / `w` / `h` / `slot` 的整数性与区间;行 token 数上界 | `PXL002` |
| 7 | **仅当 `palette` 长度 `<= 65535` 时**执行:`encoding` 是否等于由该长度派生出的档位。`>= 65536` 时**跳过本阶段**(不存在可派生的档位,比对无定义),留给阶段 9 报 `PXL005` | `PXL003` |
| 8 | `op` 名是否在八条之内 | `PXL004` |
| 9 | **引用与容量**,四类都要查:① `palette` 的格式与长度;② **已知 op 的数值 `slot`**(`fill` / `rect` / `pixel` / `line` 直接给出的那个数;`erase` **没有** `slot` 参数,它隐含写 slot 0)不得超过该档上限或 `palette` 长度;③ **所有 token 解码出的 slot**——已知 op 的 `grid`、`stamp` 引用的 sprite、以及**未被任何 `stamp` 引用的 sprite 定义**(未引用不等于不校验);④ **`stamp` 引用的 sprite 名字必须存在** | `PXL005` |

**关键**:第 4 阶段失败即返回,第 5 阶段根本不执行。于是未知 `encoding` 搭配 `grid` **只可能**得到 `PXL003`——这正是旧版扁平顺序无法给出的唯一答案。

首个失败即返回,不继续检查后续阶段。抽取侧只有阶段 1 与阶段 9(色数超限),且 `PXL006` 必须先于任何输出。

**数值 slot 与 token 解码出的 slot 是两条不同的路径,阶段 9 两条都查。** 前者是 `fill` / `rect` / `pixel` / `line` 参数里直接写的整数,根本不经过 token 解码,所以"检查 token 解出的 slot"这条覆盖不到它;`palette` 只有 1 项时,`fill` 的 `slot: 2` 就是这种情形——阶段 6 只判它是不是 0..65535 的整数,判不出它越过了 `palette`。同理,`stamp` 引用的**名字是否存在**也不是 slot 检查:没有 `sprites` 时,一个 `stamp: missing` 没有任何 token 可供检查。

**op 专属检查只对八条已知图元生效——但"对象层面的通用检查"始终执行。** 这两类必须分开说,否则会写出覆盖面过宽的规则:

- **跳过**(`op` 名不在八条之内时):成员集合与类型对位、`x` / `y` / `w` / `h` / `slot` 等数值域、形似 `grid` 的行数组、slot 引用。这些都以"知道这个 op 有哪些成员、哪些是坐标"为前提,而未知 op 无从谈起,强行校验只能靠猜,故一律留到阶段 8 报 `PXL004`。
- **照常执行**(对**任何**对象,包括未知 op):合法 JSON、**成员名不重复**(§3.2)、`op` 字段存在且是字符串。这三项是 JSON 与文档模型层面的通用约束,与"这个 op 是什么"无关。
- **文档级成员**(`width` / `height` / `palette` / `sprites` / 图层数 / 面积 / ops 计数 / 文档字节数)不受本条影响,照常检查。

于是:`{"op":"circle","x":1,"x":2}` 在**阶段 3** 就因重复键报 `PXL001`,走不到阶段 8;而 `{"op":"circle","x":99999}` 里 `x` 属 op 专属数值域被跳过,才在**阶段 8** 报 `PXL004`。

这条不定死,`{"op": "circle", "x": 99999}` 就会出现两种都"合规"的结果:一种跳过未知 op 的成员、阶段 8 报 `PXL004`;另一种把 `x` 当坐标、阶段 6 先报 `PXL002`。

**阶段 3 与阶段 5 的分界只有一条**:某一项检查是否需要知道 token 宽度。行数组的**存在性与形状**(至少 1 行、每行非空、各行等长)不需要,归阶段 3;而**行内字符是否合法**需要,因为"哪些字符合法"取决于档位(char 档与十六进制档的字符集不同),归阶段 5。**"是否为空白"不是一个可用的判据**:不同实现对 U+00A0 等码点的分类不同,必须回到 §4.2 / §4.3 的枚举集。这条分界不写死,「未知 `encoding` + `grid: []`」就会出现两个实现分别报 `PXL001` 与 `PXL003`——两句话都合规,结果不同。

### Core §11.2 码空间

`PXL001` 到 `PXL006` 在 current core 内固定,`PXL007` 到 `PXL099` 保留给后续版本(§12)。新增码必须有 conformance 负例。

## Core §12. 版本与预留

- `version` 是整数,当前恒为 `0`。**渲染器必须以 `PXL001` 拒绝任何其它值**——与其猜一个未知语义,不如停下。判定只看「是不是整数值的 0」:`1.5`(非整数)、`9223372036854775808`(超出 64 位可表示范围)、`1e99999`(同上)一律 `PXL001`,**不**走 `PXL002` 的数值域检查。把「无法表示」读成 0 会让这条 fail-closed 整个失效。
- 字段 `variant` 与 `bindings` 标为 **reserved**:current core 不定义含义,且**出现即 `PXL001`**。这是 fail-closed 的有意设计:未来文档被 current core 工具读到时应报错,而不是静默丢掉跨图复用信息后把像素写错。等出现第二个真实使用者再设计(AGENTS.md §8 O3)。
- v1 候选(本步不实现、不预留行为):
  - 16 bit 每通道(当且仅当出现真实 16-bit 素材需求)。
  - `variant` / `bindings` 的正式语义。
- 向后兼容原则:任何 v1 文档的 `version` 必须大于 0,使 current core 实现明确拒绝而不是误读。

## Core §13. 一致性语料约定

### Core §13.1 一个用例一个目录

`spec/conformance/cases/<case-path>/`,其中 `<case-path>` 与 `CASES.tsv` 首列**逐字符相同**:正例是单个 kebab-case 目录名(如 `syn-1x1-opaque`),负例是 `negative/<kebab-case>`(如 `negative/neg-format-invalid`)。负例的**叶目录名**只是 `neg-...` 那一段——列出 `case` 列时写全相对路径,不要只写叶名。

用例分**三种形态**,由目录名前缀决定(与 `CASES.tsv` 的 `case` 列同值):

> 生成型用例(§13.6)的输入文件在**运行生成器之前并不存在**;下表列的是"生成之后应当有什么"。

| 前缀 | 形态 | 判据 |
|---|---|---|
| `syn-` / `real-` | 往返正例 | §13.2a |
| `op-` / `blend-` | **仅渲染**正例 | §13.2b |
| `negative/` | 负例 | §13.2c |

**为什么必须分开**:附录 A 规定抽取器只产出 `fill` / `rect` / `grid`,且只产单图层 `normal`。因此任何含 `stamp`、`line`、`multiply` 的文档**都不可能**由任何位图抽取出来——若对它们也要求"抽取后零 diff",这些用例就是永远失败的装饰品,而不是判据。

**往返正例**(`syn-` / `real-`):

| 文件 | 必需 | 内容 |
|---|---|---|
| `input.png` | 是 | 源位图,**必须符合 §8.1 的接受集**(8 bit、非交错、色彩类型 0 / 2 / 3 / 4 / 6 之一)。**不要**为了凑契约先转成 RGBA8 入库——那会把色彩类型 0 / 3 / 4 与 `tRNS` 的解码路径整个测没了。固定为 RGBA8 的只有**期望像素流**(§13.4),不是源文件。 |
| `expected.pxl` | 是 | **规范形式**的 PXL 文本,逐字节权威。 |
| `expected.pixels.sha256` | 是 | 一行:RGBA8 原始字节流的 SHA-256(小写十六进制)+ 换行。字节流定义见 §13.4。 |
| `notes.md` | 是 | 该用例覆盖哪条规范条款、期望值怎么来的、若有偏离写清为什么。 |

**仅渲染正例**(`op-` / `blend-`):

| 文件 | 必需 | 内容 |
|---|---|---|
| `input.pxl` | 是 | 人手写的 PXL 文档。**没有** `input.png`,也没有"抽取一致"这一判据。 |
| `expected.pixels.sha256` | 是 | 同上一行格式。 |
| `notes.md` | 是 | 覆盖哪条条款、期望值怎么算出来的(逐步算式)。 |

**负例**(`spec/conformance/cases/negative/<case-name>/`):

| 文件 | 必需 | 内容 |
|---|---|---|
| `input.pxl` | **渲染负例必需** | 非法 PXL 文档,测渲染器。 |
| `input.png` | **抽取负例必需** | 非法或不受支持的输入位图,测抽取器。 |
| `expected.error` | 是 | 一行:期望的错误码,如 `PXL005` + 换行。 |
| `notes.md` | 是 | 违反了哪条、为什么期望该码,**并写明受测侧**(渲染 / 抽取)。 |

**`input.pxl` 与 `input.png` 互斥,由"受测操作"决定,不由错误码决定**:

- 渲染负例 → 只有 `input.pxl`,测渲染器。
- 抽取负例 → 只有 `input.png`,测抽取器(它根本不读 PXL)。
- **错误码与侧不是一一对应。** `PXL005` 两侧都会出现:
  - 渲染侧:`palette` 项格式错、token 指向的 slot 越界、`stamp` 引用不存在的 sprite;
  - 抽取侧:**色数超出该档容量**(如去重后 `n ≥ 65536`)——这时**根本没有 PXL 文档可读**,只能用 `input.png`。
- `PXL001`–`PXL004` 只属渲染侧;`PXL006` 只属抽取侧。

早先按错误码分派(「`PXL001`–`PXL005` 都是渲染侧」)是错的:它让抽取侧的 `PXL005` 无处安放——一张 256×256、65536 个不同非透明色的合法 PNG,尺寸与面积都合规,却只能由抽取器报 `PXL005`,而旧契约不允许为它建 `input.png` 目录。

因此 **runner 必须按目录里实际存在哪个输入文件决定跑哪一侧**,不得只读 `expected.error` 去猜;`notes.md` 必须写明受测侧,否则同一个码的两种语义无法区分。

### Core §13.2 通过判据

**13.2a 往返正例**,以下六条**同时**成立:

1. **抽取一致**:抽取器读 `input.png`,输出与 `expected.pxl` **逐字节相同**(零 diff)。这是 `expected.pxl` 必须规范形式的理由。
2. **回渲像素一致**:渲染器读 `expected.pxl`,产出的 RGBA8 原始字节流 SHA-256 等于 `expected.pixels.sha256`。
3. **跨语言闭环**:抽取器从 `input.png` 得到的 `.pxl`(即 `expected.pxl`)交给渲染器,产出与 `input.png` 解出的 RGBA8 **逐字节相同**。
4. **确定性**:抽取器两跑 `.pxl` 逐字节相同;**渲染器两跑 PNG 文件逐字节相同**(§9;跨实现之间仍只比像素)。
5. **尺寸一致**:渲染器输出 PNG 的 `width`/`height` 必须等于 `expected.pxl` 声明的值,并且等于 `input.png` 的尺寸。摘要只覆盖像素字节、不含尺寸(§13.4)——一份 2×2 的文档若被渲染成 1×4,字节序列可以完全相同,前四条一条都拦不住。
6. **输出结构合规**:输出 PNG 必须满足 §10——每通道 8 bit、色彩类型 6、非交错;**所有行的过滤器字节恒为 0**;chunk **类型**序列为 `IHDR` → `IDAT`⁺(至少一块,**可多块连续**)→ `IEND`,不出现其它类型。一个固定用过滤器 1 的渲染器,像素、尺寸、两跑字节一致**全部能过**,只有这一条能拦。**不要在这里悄悄把 `IDAT` 收窄成单块**:§10 约束的是"只写这三种类型",不是"恰好三个 chunk"。

**13.2b 仅渲染正例**,以下五条**同时**成立:

1. **回渲像素一致**:渲染器读 `input.pxl`,产出的 RGBA8 字节流 SHA-256 等于 `expected.pixels.sha256`。
2. **确定性**:渲染器对同一文档两跑,PNG 文件逐字节相同(§9)。
3. **不拘形式**:该文档本就**不是**抽取器能产出的形态(手写多图层、含 `flipX`、含非 `normal` 的 blend),渲染器必须照样接受——这一条检验的正是 §3.8"渲染器不得要求规范形式"。
4. **尺寸一致**:输出 PNG 的 `width`/`height` 必须等于 `input.pxl` 声明的值。理由同 §13.2a 第 5 条:摘要不含尺寸,必须单独断言。
5. **输出结构合规**:同 §13.2a 第 6 条。

**13.2c 负例**通过,当且仅当:实现以 `expected.error` 给出的那个码失败,且**未产出任何输出文件**(不得留半份)。

### Core §13.3 新增用例的步骤

1. 先确认本规范覆盖该行为;没有覆盖就先改规范。
2. 在 `CASES.tsv` 增一行,**八列齐全,不得留空**。列定义就是下面这张表——
   它是**规范的正文**,`spec/conformance/README.md` §3 只解释怎么用,不复述名称:

   | 列 | 取值 | 含义 |
   |---|---|---|
   | `case` | 相对路径 | 与 `cases/` 下的位置逐字符相同;负例形如 `negative/<name>` |
   | `source` | `synthetic` / `real` | 自包含 / 真实素材复制件 |
   | `form` | `single` / `batch` | `batch` 指 §13.7 的批量形态;其余一律 `single` |
   | `size` | `WxH` / `Wx(Hlo..Hhi)` / `-` | 单例写精确尺寸;批量写宽度 + 成员高度的闭区间,**或**在全部成员尺寸相同时写 `WxH`;负例写 `-` |
   | `colors` | 十进制整数 / `varying` / `-` | 非透明 texel 去重数(= `palette` 长度);批量写 `varying`,**或**在全部成员相同时写该整数;负例写 `-` |
   | `encoding` | `char` / `index` / `index4` / `A..B` / `-` | 期望档位;批量写闭区间(`char < index < index4`,左端不得宽于右端),**或**在全部成员相同时写单值;负例写 `-` |
   | `covers` | 自由文本 | 覆盖点。负例必须以 `PXL00N(受测侧):` 开头 |
   | `input` | `committed` / `generated` | 输入入库 / 按 §13.6 配方生成 |

   **`form` 是判定批量形态的唯一依据**:不看目录里有没有 `manifest.tsv`,更不看
   `covers` 里写了什么(与 §13.6 「判定不看 `covers` 的自由文本」同一条原则)。
   `form=batch` 的行必须同时有 `manifest.tsv` 与 `members/`;`form=single` 的行不得有。
3. 建目录,放齐 §13.1 要求的文件。往返正例的 `expected.pxl` **必须**由附录 A 的规则生成,不得手调空白;仅渲染正例的 `input.pxl` 允许手写,但应写成规范形式(§3.7)以便 review,并靠 §13.2b 判定,而不靠对比文本。
4. 按**形态**验证,不要一套流程套三种:
   - **往返正例**:两条都跑——抽取器从 `input.png` 产出 `expected.pxl`,渲染器从 `expected.pxl` 回渲出 `expected.pixels.sha256`。
   - **仅渲染正例**:**没有** `expected.pxl`,只验证渲染器从 `input.pxl` 回渲出 `expected.pixels.sha256`。**不得**要求"抽取器产出它"——那种验证不可能执行,`op-stamp-flip` 之类根本不存在对应的 `input.png`。
   - **负例**:只跑受测那一侧,并确认它报出 `expected.error` 且不留输出文件。
5. 在 `notes.md` 写清覆盖的条款编号,负例还要写明受测侧。

### Core §13.4 `expected.pixels.sha256` 的字节流定义

- 顺序:逐行、行内从左到右,**自上而下**(第一行先)。
- 每像素 4 字节,顺序 R, G, B, A。
- 无行间填充、无对齐、无头尾附加字节。
- 总长恒为 `4 × width × height`。

### Core §13.5 语料不得依赖外部素材

`synthetic` 用例必须自包含:**输入由用例生成器产出,默认入库**。唯一例外是输入超过 4 MiB 的用例,按 §13.6 改为"按配方生成、不入库"。`real` 用例登记原始来源路径,但**入库的是复制件**并附 `samples/PROVENANCE.md` 记录。

### Core §13.6 生成型用例(输入不入库)

有些用例的输入本身就是几十 MB——它们测的正是"数量/字节上限"这个行为,输入小了根本测不出来。这类用例**不提交输入**,改为按配方生成;否则 64 MiB 的负例会把仓库撑爆,而那恰好是它要测的东西。

**判定**:输入文件超过 **4 MiB** 的用例走本节。不超过 4 MiB 的**必须入库**,没有例外,不许"图省事"走生成路径。

**配方**:这类用例的 `notes.md` 必须包含一节 `## recipe`,内容是单个 JSON 对象:

```json
{"generator": "<名字>", "params": {}, "expectedInputBytes": 0, "expectedInputSha256": ""}
```

`expectedInputBytes` 与 `expectedInputSha256` 是生成结果的**指纹**,不是提示:runner 用它判断生成物是否正确,而不是只看"文件存在"。

**哪些用例是生成型,由 `CASES.tsv` 的 `input` 列判定,不看 `covers` 的自由文本。** 这一列不能省:`--all` / `--check` 的枚举只能从"哪些行声明自己是生成型"出发;若改成"遍历有配方的用例",枚举就退了半步——**漏写配方会被读成"这一条没有生成任务"**,于是空集合通过,而那正是本节要防的事。所以两个方向都要查:`input = generated` 却无配方 → 失败;`input = committed` 却有配方 → 失败(索引自相矛盾)。
- 反向也成立:`input = committed` 的行**不得**带 `## recipe`

**生成器入口(固定,不得各家自定)**:

- 路径:`spec/conformance/tools/gen_cases.py`(该脚本**不属于本次规范交付物**:本节固定的是它的接口与确定性要求,实现留到"生成语料"那一步——现在把它写死,是为了届时不至于两个人各写一份生成脚本)
- 运行时:Python 3.8+,**仅标准库**(与 `AGENTS.md` §4.2 同一约束)
- 命令(**`<py>` 表示本机任一可用的 Python 3.8+ 解释器,不是固定字符串**;常见写法:`python`、`py -3`、`python3`):
  - `<py> spec/conformance/tools/gen_cases.py <case-path>` —— 在该用例目录下写出输入文件,已存在则覆盖。**`<case-path>` 就是 `CASES.tsv` 首列的完整相对路径,逐字符相同**,例如 `negative/neg-doc-too-large`;不接受只写叶名 `neg-doc-too-large`,也不接受绝对路径。
  - `<py> spec/conformance/tools/gen_cases.py --all` —— 遍历 `CASES.tsv` 中 `input = generated` 的**所有**行并逐个执行;任何这样的行若没有 `## recipe`,以非零退出码结束;
  - `<py> spec/conformance/tools/gen_cases.py --check` —— **不写文件**,遍历**所有**配方逐条校验,下列任一情形都以**非零退出码**结束:① 输入文件**不存在**(不得因为"没有可检查的文件"而当成通过——空集合通过是这里最容易踩的坑);② 字节数不等于 `expectedInputBytes`;③ SHA-256 不等于 `expectedInputSha256`;④ `input = generated` 的行没有 `## recipe`;⑤ `input = committed` 的行却有 `## recipe`(索引自相矛盾)。
- **不要钉死 `python3`**:某些平台上它是 Microsoft Store 的占位别名——文件存在、执行失败(本仓库的开发机上正是如此),而 `python` 与 `py -3` 正常。钉死拼写会让生成型用例在一整类机器上不可执行,正是本节要避免的失败模式。脚本本身必须能被任意 3.8+ 解释器以文件路径直接运行。
- 生成器必须**确定**:同一配方任意次运行输出逐字节相同;不使用时钟、随机、locale、文件系统遍历顺序(§9)。

**runner 的义务**:

- 跑生成型用例前必须先执行对应的生成命令;
- **`--check` 失败等同于该用例失败**,不得跳过,也不得当成"环境问题"绕过;
- 生成物**从不**入库;仓库应忽略这些目录里的输入文件名。

**为什么入口必须写死**:不写死,每个实现方会各写一个生成脚本,"同一份语料"就变成两份不同的字节——而这正好废掉本项目赖以对齐的唯一手段。

### Core §13.7 批量用例(suite)

§13.1 的目录契约默认**一条用例 = 一个输入文件**。但索引里有三条不是:`real-chain-overlay-dedupe` 要比对两条路径是否同图;`real-fluid-source-255` 与 `real-item-material-family-400` 分别要处理 255 / 400 个文件。它们塞不进单例形态,所以单列本节。

**批量形态**:`CASES.tsv` 里 `form=batch` 的用例(§13.3)。它比单例多出这些要求:

- `cases/<name>/manifest.tsv`:制表符分隔,首行表头 `member` / `input` / `encoding` / `colors`;每个成员一行。`member` 是 kebab-case 标识,同时就是子目录名。
- **`input` 列是来源记录,不是被测文件的路径。** 被测文件恒为 `members/<member>/input.png`,与 `input` 列无关——否则 runner 无法唯一确定该打开哪份文件。`input` 当前只允许下面这一种取值,其余一律非法(裸文件名、绝对路径、以 `members/` 开头、以及 `samples/...` 这种无前缀写法都非法):
  - `sample:<samples/ 下的相对路径>` —— 真实素材;该路径必须在 `samples/PROVENANCE.md` 里登记。
  - ~~`generated:<配方名>`~~ —— **当前不允许**。§13.6 的生成器以 `CASES.tsv` 的 `case` 列为寻址单位,而批量成员不在索引里;要支持"生成型成员"就得再定义一套成员寻址与递归发现规则,否则会出现"suite 根没有配方、成员有配方"这种**合法却在规则上悬空**的状态——runner 找不到该跑什么。在确有需求之前不引入这条分支。
- `input` 列的取值必须与 `members/<member>/notes.md` 里声明的来源一致;不一致即该用例失败。
- `cases/<name>/members/<member>/`:结构与 §13.1 的单例完全一致(`input.png` / `expected.pxl` / `expected.pixels.sha256` / `notes.md`)。
- `notes.md` 必须含 `## aggregate` 一节,写明该用例的**聚合判据**。聚合判据必须可判定,不能写成"统计一下"。

**判据**:每个成员按 §13.2a / §13.2b 各自通过,**再加** `## aggregate` 的聚合断言。已知两类:

- **去重组**(`real-chain-overlay-dedupe`):`## aggregate` 列出**必须产出逐字节相同 `expected.pxl`** 的成员组;判据就是逐字节相同,不是"看起来一样"。
- **批数组**(`real-fluid-source-255`、`real-item-material-family-400`):`manifest.tsv` 的行数 = 成员目录数 = `## aggregate` 里写死的成员数。每个成员通过,且三者计数一致,聚合才通过。

**`manifest.tsv` 与实际成员不一致即该用例失败**(缺目录、多目录、行数对不上)。这一条不是形式主义:没有它,"255 个成员必须逐一有判定"只是一句自述,无法核对到底跑了几个。

**已知缺陷成员(defect member)。** 真实素材里**确有其事**地存在容器合法性缺陷:`block/fluid/source/` 的 255 个 PNG 中,有 10 个的 `iCCP` chunk CRC 损坏(其余 chunk 全部正确、像素完好)。按 §8.5「每个 chunk 的 CRC 都必须校验」,这 10 个**只能是 `PXL006`**,不可能有 `expected.pxl`——把它们写成往返正例,要么迫使实现放宽 CRC,要么让用例永远失败,两者都不可接受。

因此批量用例允许一类成员:

- 成员目录结构与 §13.1 的**负例**一致:`input.png` + `expected.error` + `notes.md`(没有 `expected.pxl`、没有 `expected.pixels.sha256`);
- 判据按 §13.2c:实现必须以 `expected.error` 的码失败,且不产出任何输出文件;
- `notes.md` 必须写明**为什么这是素材缺陷而不是实现缺陷**,并附实测的存储 CRC 与计算 CRC;
- `manifest.tsv` 仍为每个成员一行,缺陷成员的 `colors` 与 `encoding` 写 `-`;`## aggregate` 的计数判据改为「正例成员数 + 缺陷成员数 = `## aggregate` 里写死的成员数」,两者都要写死具体数字,不得写"若干"。

目前只有一个用例用到它:`real-fluid-source-255` 是 **245 个往返正例 + 10 个已知缺陷成员**,合计 255。`aerotheum.png` **既是这 10 个成员之一**(算在 245 之外的 10 里),**另有**一条独立单例负例 `negative/neg-real-aerotheum-iccp-crc` 专门钉"真实素材的坏 iCCP 必须被拒"这件事——两者不冲突,也不能相互替代:批量成员证明"这 10 个都拒",单例证明"这一个拒得对"。建 `manifest.tsv` 时 `aerotheum` 是那 10 行之一,不要因为它另有单例就从批量里删掉。

**不要**把"已知缺陷成员"当成放宽规则的入口:只有**素材侧**的容器缺陷才适用,并且必须先有一份实测记录(存储值 / 计算值 / 受影响文件清单)。实现侧的任何不合规仍旧是缺陷。

## 附录 A(规范性)规范抽取策略

没有本节,`expected.pxl` 就不可能"零 diff":不同实现会选出不同的合法 op 序列。本节把抽取器的输出**唯一确定**下来。渲染器**不需要**实现本节,只需接受任何合法 PXL。

1. 解码输入为 `width` × `height` 的 slot 网格;按 §4.4 分配调色板;按 §4.5 派生 `encoding`。
2. 若**全部像素**是同一 slot `S`,则 `ops = [fill S]`,结束(整图纯色 → 一条 `fill`)。
3. 否则逐行分类。**段**指行内极大的同色连续区间。一行称为 **RUNNER 行** 当且仅当其**所有**段长度不小于 3(`MIN_RUN = 3`);否则称为 **GRID 行**。
4. 把行按分类切成**极大的同类型连续块**,按行号升序。
5. 对每个 **RUNNER 块**(行 `y0..y1`):逐行从左到右取段 `(x, w, slot)`;若上一行在**同一块内**存在完全相同的 `(x, w, slot)`,则把那条 `rect` 的 `h` 加 1;否则新起一条 `rect`。`rect` 按首次出现的行序、再按 `x` 升序输出。
6. 对每个 **GRID 块**(行 `y0..y1`):输出**一条** `grid` op,`x = 0`、`y = y0`,`grid` 为该块各行的 token 串。
7. `ops` 按块的先后排列。文档固定为**单图层**:`name = "base"`,`blend = "normal"`。
8. **ops 预算与全局回退**。若该层的 op 数超过 `OPS_CAP = 32768`,则**整层退化为一条覆盖全图的 `grid` op**(所有行拼成一个 grid),丢弃已生成的全部 `rect` 与 `grid` 块。
   - 回退是**纯函数**(只取决于像素值),因此仍满足"同输入同输出";
   - 回退后像素不变,零 diff 仍可判定;
   - 这条不是优化,而是让 §5.0.2 的 `ops` 上界成为**被构造保证**的事实:没有它,`65535 × 4`、段宽恒 3、相邻行反色的合法图会产出 87,380 条 `rect`,抽取器既不能输出非法文档,也没有拒绝路径。
9. 抽取器**绝不**产出 `pixel` / `line` / `mirror` / `erase` / `stamp`。这五条由图元用例(手写 `expected.pxl`)覆盖,不由抽取器覆盖。
10. 规范输出**不含** `sprites` 成员,也不含任何 §3.7 未列出的成员;成员顺序与可选布尔省略规则见 §3.7。否则"零 diff"会先在成员顺序或空 `sprites` 上失败,与像素无关。

`MIN_RUN = 3` 是一项**本规范新增的判定常数**;AGENTS.md §3.3 只要求"行内连续同色段 → rect",未给阈值。取 3 的依据:长度为 1 或 2 的段写成 `grid` 更短也更易读。该常数已按**落地假设**处置(C-5),实现方直接按 3 实现;若要改,改此处一处并重新生成全部 `expected.pxl`。

**自检性质**:对任一正例,按本节产出的 `ops` 渲染结果必须等于原图逐像素;否则抽取策略实现有错。

## Extension §3. 文档模型（current）

### Extension §3.1 文件形态

沿用 Core §3.1：UTF-8 文本、允许开头 BOM、LF 换行、单一顶层 JSON 对象。文档 UTF-8 字节数上限
沿用 Core §5.0.2（64 MiB，超过报 `PXL002`）。

### Extension §3.2 顶层字段

current 文档的顶层成员集合**恰好**是：

| 成员 | 必需 | 说明 |
|---|---|---|
| `format` | 是 | 字符串，恒为 `\"PXL\"` |
| `version` | 是 | 整数 `1` |
| `width`、`height` | 是 | 画布尺寸，语义与上界沿用 Core §5.0.1 / Extension §5.0.2 |
| `encoding` | 是 | `char` / `index` / `index4`，语义与派生规则沿用 Core §4 |
| `palette` | 否 | 调色板，沿用 Core §4.4 |
| `layers` | 是 | 图层数组，沿用 Core §6（至少 1 个） |
| `sprites` | 否 | 文档内 sprite，沿用 Core §3.7 |
| `assets` | 否 | 外部 asset 声明，见 Extension §5 |
| `params` | 否 | 参数声明，见 Extension §6 |

未在上面列出的成员一律 `PXL001`（core 的 `variant` 与 `bindings` 在 current 中**仍被拒绝**：
多输出由调用方的 target 表达，不进入文档语义）。

### Extension §3.3 其余一律沿用 core

图层名与 sprite 名语法、重名规则、行数组形状、三档 token 字符集、八条 op 的参数集合与语义、
三种 blend 的整数公式与取整、透明度语义、单文档资源上界、光栅工作计数口径——**全部**按 core 执行，
本文件只增加 Extension §5、Extension §6 两处扩展与 Extension §5.3 的 `stamp` 来源扩展。

## Extension §4. 名字与引用

### Extension §4.1 名字语法

参数名与 asset 名必须匹配：

```text
[a-z][a-z0-9_]{0,63}
```

即：小写 ASCII 字母开头，其后为小写字母、数字或下划线，总长 1..64。名字在**各自的表内**唯一：
`params` 内重名或 `assets` 内重名都是 `PXL001`。参数名与 asset 名不共享命名空间，
但**同名也不构成错误**（两者在语法位置上一望可分）。

### Extension §4.2 参引语法

参引是**字符串** `\"$name\"`，其中 `name` 满足 Extension §4.1。参引**只能**出现在 Extension §6.2 的白名单位置。
在其它位置出现以 `$` 开头的字符串（无论是否形如参引）一律 `PXL012`——不存在转义机制，
因为白名单位置的合法字面量都不以 `$` 开头（palette 是八位大写十六进制、逻辑路径是 ASCII 小写
不含 `$`、符号名以字母开头、整数与布尔不是字符串）。

## Extension §5. 外部 asset

### Extension §5.1 声明

`assets` 是对象：成员名是 asset 名（Extension §4.1），值是对象，成员集合**恰好**为：

| 成员 | 必需 | 说明 |
|---|---|---|
| `kind` | 是 | 字符串，只能是 `\"pxl\"` 或 `\"png\"` |
| `path` | 是 | 字符串，逻辑路径（Extension §7），**必须是字面量**，不得是参引 |
| `params` | 否 | 子文档参数映射，见 Extension §5.2；`kind: \"png\"` 时**不得**出现 |

`kind` 缺失、非字符串、或字符串不属于 `{\"pxl\",\"png\"}` 都是 `PXL001`（core 的枚举越界口径）。
`path` 缺失、非字符串是 `PXL001`；是字符串但不符合 Extension §7 是 `PXL008`。

一个文档最多声明 4096 个 asset；超过报 `PXL002`。**声明数量与是否被使用无关**：未选中的声明
也计入本上限（PRD Extension §12.1）。

### Extension §5.2 子文档参数映射

`params` 是对象：键是**子文档**声明的参数名，值是强类型常量或父文档参引 `\"$parent\"`。

- 键必须是子文档 `params` 里存在的参数名；不存在 → `PXL012`；
- 值类型必须与子文档同名参数的类型一致；不一致 → `PXL012`；
- 子文档的必需参数（无 `default`）在本映射里缺项 → `PXL012`，错误定位到**本 asset 声明**，
  并带上引用链；
- 子文档可选参数缺项时，取子文档的默认值；
- 不做同名参数的隐式透传：父文档有 `c` 而本映射不写 `c`，子文档不会自动拿到它；
- `kind: \"png\"` 的声明出现 `params` → `PXL001`（结构错）。

### Extension §5.3 `stamp` 的来源扩展

current 的 `stamp` 参数集合恰好是 Core §5.8 的参数集合**再加上** `asset`，且：

- `sprite` 与 `asset` **必须恰好出现一个**；都出现或都不出现 → `PXL001`（已知 op 的参数集合不符）；
- 其余参数（`x`、`y`、可选 `flipX`、`flipY`）语义与 Core §5.8 完全一致：整数坐标、
  先 X 后 Y 翻转、逐点越界裁剪、整图放置、当前图层的整数 blend；
- asset 来源的像素尺寸**就是**被引用资源解码后的宽高，不存在缩放或插值；
- 引用的 asset 名必须已声明：未声明 → `PXL005`（与 core "stamp 引用不存在的 sprite" 同码、同阶段）；
- 被引用的 PXL 只贡献**最终合成位图**，其内部图层、sprite、palette 与局部名字一律不可见。

## Extension §6. 参数与 bindings

### Extension §6.1 声明

`params` 是对象：成员名是参数名（Extension §4.1），值是对象，成员集合**恰好**为：

| 成员 | 必需 | 说明 |
|---|---|---|
| `type` | 是 | `\"color\"` / `\"integer\"` / `\"boolean\"` / `\"asset\"` / `\"sprite\"` |
| `default` | 否 | 该类型的规范值，见 Extension §6.4 |

缺 `default` 的参数是**必需参数**。`type` 缺失或不在五个值之内 → `PXL001`；`default` 与
`type` 不符 → `PXL012`（例如 `type: \"integer\"` 配 `default: 1.5`）。

### Extension §6.2 替换位置白名单

参引只允许出现在下表的字段上，**其它位置一律 `PXL012`**：

| 参数类型 | 允许的替换位置 |
|---|---|
| `color` | `palette` 数组的**元素**（替换后必须是八位大写十六进制） |
| `integer` | 已知 op 的 `x` / `y` / `x0` / `y0` / `x1` / `y1` / `w` / `h` / `slot`；`mirror` 的 `from` / `to` 对象里的同名坐标也算（嵌套坐标与直接成员同权）。参数替换**不扩展任何 op 的成员集合**。**只允许替换该 op 原有的整数成员**——不存在的成员（如 `fill.x`）不因参引而变成合法 |
| `boolean` | `stamp` 的 `flipX` / `flipY` |
| `asset` | `stamp` 的 `asset`（值必须是本文件已声明的 asset 名） |
| `sprite` | `stamp` 的 `sprite`（值必须是本文件已声明的 sprite 名） |

参数**不得**改变：文档版本、`format`、`encoding`、`width` / `height`、图层数量或顺序、
op 的数量或种类、asset 的 `kind` 或 `path`、输出路径。出现在这些位置 → `PXL012`。

### Extension §6.3 bindings

compiler 接受入口文档与一组显式 bindings。规则固定为：

- bindings 只能绑定**入口**文档声明的参数；未声明 → `PXL012`；
- 必需参数缺失 → `PXL012`；类型不匹配 → `PXL012`；
- 绑定值一律以**规范字面量**形式给出（CLI 用 `--bind name=value`），实现必须按声明类型解析：把 `1.5`、`abc` 绑给 `integer`，或把 `xyz` 绑给 `color`，都是 `PXL012`；
- bindings **不影响** resolver 的查找范围：它既不能引入新路径，也不能改变 asset root；
- bindings 在通过校验后被转换为**规范 bindings**：按参数名 ASCII 升序排列的强类型映射，值为
  该类型的规范形式（Extension §6.4）。**规范 bindings 就是 target 身份的一部分**（PRD Extension §11.2）。

### Extension §6.4 类型的规范形式

| 类型 | 规范形式 | 说明 |
|---|---|---|
| `color` | `^[0-9A-F]{8}$` | 与 core palette 项同格式；小写一律非法 |
| `integer` | 十进制整数，无前导零、无 `+`、无 `.`、无指数 | `-0` 即 `0`；身份是数学整数值，不是字符串 |
| `boolean` | JSON `true` / `false` | 只有这两种 |
| `asset` | 已声明的 asset 名字符串 | 只在该文档声明过的名字里取值 |
| `sprite` | 已声明的 sprite 名字符串 | 同上 |

`integer` 的取值域沿用 Core §5.0.1 的整数域；替换完成后由目标字段按原规则校验（见 Extension §6.5）。

### Extension §6.5 参数阶段与替换

参数阶段的位置是**版本分派之后、具体字段值校验之前**（PRD Extension §10.5）：

1. 校验 `params` 声明语法（Extension §6.1）、参引语法（Extension §4.2）与 bindings 集合/类型（Extension §6.3）；
2. 任何一条不满足即 `PXL012`，**本阶段失败就结束**，不继续后面的阶段；
3. 完成替换，得到一份**不含参引的具体文档**；
4. 对具体文档按目标字段**原有的**阶段与错误码继续检查（Extension §11.2 表第 4 行起，即 core 阶段 3 起）。

由此固定下来的判定（实现不得另选）：

| 情形 | 码 |
|---|---|
| `integer` 参数替换到 `slot` 后越过 palette 长度 | `PXL005`（不是 `PXL012`） |
| `integer` 参数替换后坐标越出 Core §5.0 数值域 | `PXL002` |
| 参引出现在 `width` 等禁止位置 | `PXL012` |
| `asset` / `sprite` 绑定到未声明的名字 | `PXL012` |
| `color` 参数替换后不是八位大写十六进制 | 由 Core §11 阶段 9 报 `PXL005` |
| 替换后的 op、blend、palette 或资源预算 | 不获得任何参数豁免，按原规则判 |

## Extension §7. 逻辑路径

PXL 文档内的 `path` 是**可移植逻辑路径**，不是宿主文件系统字符串。语法**恰好**是：

- 只允许 ASCII 小写字母 `a`–`z`、数字 `0`–`9`、`-`、`_`、`.`、`/`；
- 分隔符只能是 `/`；反斜杠 `\` 一律非法，**不做转换**；
- 大小写敏感；大写字母一律非法，**不自动转小写**；
- 禁止绝对路径（前导 `/`）、盘符（`C:`）、UNC、URL、空段（`a//b`）、尾随 `/`（`a/`）；
- `.` 段非法；`..` 段允许出现，但只能参与下述规范化；
- 单个路径段最长 255 字节，规范化后的完整逻辑路径最长 4096 字节；
- 规范化规则固定为：先按 `/` 切段，逐段处理，`..` 弹出一段；弹出时栈已空即**字符串层逃逸**；
  结果段用 `/` 重新连接，作为**唯一名称**用于依赖身份、循环检测与清单输出。

引用**相对声明该引用的文档所在的逻辑目录**解析。规范化后的结果必须仍位于 asset root 内（Extension §8）。
违反上述任一条 → `PXL008`。

## Extension §8. Asset Root、入口与 Resolver

### Extension §8.1 入口

每次编译必须显式提供 asset root 与**入口的逻辑路径**。

- 入口文档必须位于 asset root 内；
- current 的 core 入口**不接受**"只有原始字节、没有逻辑身份"的调用——没有身份就没有相对解析的基准；
- core 保留纯字节解析 API（core 无外部依赖，不需要身份）。

### Extension §8.2 Resolver 合同

compiler core 只依赖抽象 resolver，**不直接搜索文件系统**。resolver 对一个逻辑路径返回四种结果之一：

| 结果 | 含义 | 映射 |
|---|---|---|
| `OK` | 命中，返回原始字节 | —— |
| `MISSING` | 该逻辑路径不存在 | `PXL009` |
| `CASE_MISMATCH` | 只有大小写折叠后才相等 | `PXL008` |
| `ESCAPE` | 规范化或真实路径落到 root 之外 | `PXL008` |

resolver 不得搜索备用目录、不得读环境变量、不得联网。
上述结果描述依赖语义；标准文件系统 resolver 的宿主权限、锁或读取失败按 Extension §8.4 单独传播，
不得折算成 `MISSING` 或文档超限。

### Extension §8.3 平台无关的内存 resolver fixture

conformance 使用**内存** resolver：它以逻辑路径为键保存字节，**同时保存每个路径段的原始拼写**。
判定固定为：完全一致 → `OK`；仅大小写折叠后相等 → `CASE_MISMATCH`；否则 `MISSING`。
因此大小写规则与 `..` 逃逸都能在**平台无关**的语料里判定（PRD Extension §13.2）。

### Extension §8.4 标准文件系统 resolver（只进平台测试）

实现自带的标准 resolver 另外必须：把 root 与目标解析为真实路径；用**路径段关系**判断是否在 root 下
（不做字符串前缀判断）；拒绝任何经 symlink、junction 或其他重解析点逃出 root 的目标（仍报 `PXL008`）；
在大小写不敏感的文件系统上仍校验每个逻辑路径段的实际拼写。这三类只用各平台的 resolver/CLI 测试覆盖，
不进语言语料；权限、锁、临时文件与原子替换失败属 CLI/I/O 错误，**不使用 PXL 错误码**。

## Extension §9. 依赖图、循环、遍历与清单

### Extension §9.1 依赖图

对一组给定的入口 bindings，compiler 必须在**任何光栅化开始之前**确定实际依赖图：

- `kind: \"pxl\"` 的 asset 是图节点；`kind: \"png\"` 的 asset 是叶节点；
- 所有 asset 声明都必须通过字段、类型（Extension §5.1）与逻辑路径语法（Extension §7）校验，**无论是否被选中**；
- **只有**被当前 target 实际选中的声明才会被读取，并进入该 target 的依赖清单；
- bindings 生效后，当前文档实际使用的外连边在渲染前确定；
- 递归读取并校验全部被选中的 PXL 后，依赖图固定；之后才开始光栅化。

这与 core 的 sprite 校验哲学不同，必须写清：**sprite 是文档内数据，始终全量校验；asset 是外部资源，
声明本身全量校验，但资源读取与存在性检查按当前 target 的实际选择执行**（PRD Extension §11.1）。

### Extension §9.2 身份

| 身份 | 定义 |
|---|---|
| 文件身份 | 规范化逻辑路径 |
| 渲染节点身份 | 规范化逻辑路径 + 规范 bindings（Extension §6.3） |
| 循环检测身份 | 规范化逻辑路径，**不考虑** bindings |

同一 PXL 路径只要再次出现在当前递归栈中即为循环（`PXL010`）；**改变 bindings 不能构造递归**。

### Extension §9.3 遍历与报错顺序

- 当前文档**实际使用的** asset 名按 ASCII 升序访问；
- 同一文档内 op 按文档顺序处理；
- 第一个失败按上述固定顺序报告；
- 每个错误必须携带：根入口的逻辑路径、实际失败文件的逻辑路径、完整引用链、静默码与一句说明。
- 被引用文档自身的 `PXL001`..`PXL012` **原样传播**，只增加引用链，不包装成通用的依赖错误。

### Extension §9.4 依赖清单

compiler 返回的依赖清单表示**当前 target 实际读取的源文件**，不表示渲染节点或缓存项。
TSV schema 固定为四列：

```text
role<TAB>kind<TAB>logical_path<TAB>sha256_bytes
```

- `role`：`entry` 或 `dependency`；第一行**必须**是唯一入口；
- `kind`：`pxl` 或 `png`；
- `logical_path`：规范化逻辑路径；
- `sha256_bytes`：源文件**原始字节**的小写 SHA-256（保守失效口径：同一 PNG 只要重新编码后字节
  变化，target 就必须失效）；
- 其余行按 `logical_path` 的 ASCII 升序排列；每个实际源文件**只出现一次**（同一 PXL 以不同
  bindings 渲染仍只有一行）；未选中的 asset 不出现；
- 不记录像素摘要、bindings、compiler 版本或运行时指纹——像素摘要属输出一致性判据，bindings 属
  target 身份，运行时指纹属外部缓存键，三者都**不得**混进清单的语言语义部分。

## Extension §10. 资源预算

### Extension §10.1 单文档

每个文档（core 与 current 同）仍分别受 Core §5.0.2 的全部上界约束，超过报 `PXL002`。current 追加：

| 项目 | 上界 |
|---|---:|
| 每文档 `assets` 声明数 | 4,096 |
| 每文档 `params` 声明数 | 256（本规范自定的封口值；PRD 未规定，取此值使上界可判定） |

asset `stamp` 的写入面积**不计入**上表的单文档 `2^22` 光栅上限：写多少取决于被引用资源的尺寸，
而单文档预算属阶段 6，那时 asset 尺寸还没解析（Extension §11.2 阶段 R2 才拿到）。它按 Extension §10.3 的会话口径计入
**全局光栅工作**，同一依赖被多次 stamp 时每次各计一次。

### Extension §10.2 编译会话全局

一个 target 的递归编译额外受下列上界约束，任一先达到都报 `PXL011`：

| 项目 | 上界 |
|---|---:|
| PXL 引用最大深度 | 64 |
| 唯一 PXL 渲染节点数（路径 + bindings） | 4,096 |
| 唯一实际源文件数（入口 + PXL + PNG） | 8,192 |
| 累计 PXL UTF-8 字节数（按唯一文件） | 64 MiB |
| 累计 PNG 解码像素数（按唯一文件） | 2^24 |
| 全局光栅工作 | 2^24 次像素写入 |

全部上界都是「不超过」语义：**恰好等于上限合法，只有严格超过才报 `PXL011`**。深度上限 64 意味着 64 层合法、65 层越界；全局光栅上限 2^24 意味着恰好 16,777,216 次写入合法。这条必须
写死，否则「恰好等于上限」的正例在任何实现上都会红得莫名其妙。

"唯一渲染节点数"与"唯一实际源文件数"是**两种独立计数，不得互相折算**。清单一行对应一个唯一实际
源文件，因此清单行数天然不超过 8,192，不另设可能与之冲突的清单上限（PRD Extension §12.2）。

### Extension §10.2.1 驻留内存（不是语言语义）

Extension §10.2 的六条上界约束的是**写入量**与**图规模**，**不约束**实现同时驻留的像素缓冲。
编译一份引用了若干大尺寸依赖的文档时，实现需要在内存里同时持有被合成的节点位图；
这份工作集的大小由**依赖面积**决定，不产生任何 PXL 码：

```
工作集下界 ~= 4 字节 x (同时被合成的最多 K 个节点的像素面积)
```

因此：

- **规范不承诺任何具体的内存上界**，也不规定宿主必须能处理多大的图；
- 一份在 Extension §10.2 六条上界内**全部合法**的文档，仍可能因为工作集超出宿主可用的堆/地址空间而失败；
  这是**实现/部署**层面的资源不足，不是 PXL 错误，不得映射为 PXL011 或任何其它 PXL 码；
- 实现必须以**受控方式**报告这类失败（不泄漏堆栈），由调用方按宿主资源处理；
- 构建方在引用大尺寸素材时应按上式预留内存；[复核夹具 r03-original](../tests/fixtures/r03-original/README.md) 是一份可复跑的例子：
  1x1 入口引用 18 个 2048x2048 依赖，工作集约 288 MiB。

本条是无须判定的说明性条款（不产生正负例）；将来若要把驻留量变成**错误条件**，必须先在此处
定义口径（计入哪些缓冲、峰值怎么取、跨实现如何对齐），再补语料。

### Extension §10.3 全局光栅计数

沿用 Core §5.0.2 的逐 op 计数口径，并追加 current 规则：

- 每个**唯一** PXL 渲染节点的内部 op 工作计一次；
- 每个父文档中的 asset `stamp` 按**实际裁剪后**的写入面积计一次；同一依赖被多次 stamp 时，每次
  都计；
- 缓存是否命中只影响运行时间，**不影响**预算计数；
- 不得以"缓存命中"降低语义预算。

### Extension §10.4 上界的封口复核

Core §5.0.2 的教训是：上界必须是一组**互相封口**的数字，否则会出现"每一项都合法、合起来做不到"的输入。
current 的三个会话级上界关系如下（这是本节的判定，不是实现建议）：

1. **唯一渲染节点数 ≤ 4,096 与唯一源文件数 ≤ 8,192 不可互相折算。** 节点身份含 bindings，因此
   同一文件的多个 bindings 会产生多个节点、却只占一个源文件；反之 PNG 叶节点只计文件不建渲染节点。
   两种计数各自独立判定，任一先到即 `PXL011`。
2. **清单行数天然 ≤ 唯一源文件数 ≤ 8,192。** 清单一行对应一个唯一**源文件**（Extension §9.4），所以不需要
   再设一个可能与之冲突的清单上限——设了反而会造出"其余各项合法、只因清单条数被拒"的输入，
   那正是 Core §5.0.2 修过的同一种病。
3. **深度先于总量。** 深度上限在**进入**更深一层之前判定：一份链长 65 的依赖图即使总字节数只有
   几 KB，也报 `PXL011`，而不是先读完再报。
4. **全局光栅工作（2^24）与单文档上界（2^22）的关系。** 单文档光栅工作仍是 2^22（core 口径），
   而会话级是 2^24：至多 4 个满额文档的工作量。一份"每个文档都恰好 2^22、链深为 5"的图必然触发
   会话上限，这是有意的——单文档合法不等于整棵树合法。
5. **累计 PXL 字节（64 MiB）与单文档上限（64 MiB）同值不是巧合**：它保证"最坏情况下一份满额文档
   仍可编译"，同时把"拆成多份小文档绕过单文档上限"这条捷径关掉。

## Extension §11. 错误码与完整报错阶段表

### Extension §11.1 current 新增码

| 码 | 触发条件 |
|---|---|
| `PXL007` | 任意入口或被引用文档的 `version` 位于分派域 `0..65535`，但本 compiler 不支持该版本 |
| `PXL008` | 逻辑路径非法、字符串规范化逃逸、大小写不匹配，或标准文件系统 resolver 检出真实路径逃逸 |
| `PXL009` | 实际选中的依赖缺失、不可读（宿主 I/O 错误见 Extension §8.4），或声明类型与实际资源不符 |
| `PXL010` | 直接或间接循环引用 |
| `PXL011` | 依赖深度、总量或编译会话预算超限 |
| `PXL012` | 参数或 bindings 缺失、未声明、类型不匹配、非法替换位置或映射不完整 |

**两个码的边界（"声明类型" vs "PNG 是否合法"）**：声明的 `kind` 与该资源的实际字节**不符**时
归 `PXL009` —— 例如声明为 `"png"` 而字节缺少 PNG 签名（含短于 8 字节）；**有**正确的 PNG 签名但
结构不符合 Extension §8.3 的，归 `PXL006`。两者不是"PNG 相关错误一律 `PXL006`"，也不是"任何 PNG 报错都算
类型不符"。

`PXL013` **保留**给未来可能限制 asset kind 集合的语言版本：PXL current **永不产生** `PXL013`，
也不要求对应负例；current 的错误码范围止于 `PXL012`。current 中 `kind` 缺失、非字符串或不属于
`{\"pxl\",\"png\"}` 都是 `PXL001`。版本分派**先于** asset kind 校验：读到一个 `version: 2` 的
子文档永远是 `PXL007`（PRD Extension §13.1）。

### Extension §11.2 阶段表（顺序即优先级）

**首个失败即返回**，不继续后续阶段。本表是 Core §11.1 九阶段表的**插入与追加**：core 阶段编号保持
其原义，current 只在其中插入三个阶段（D、P）并在之后追加四个阶段（R1–R4）。core 文档永远不会进入
阶段 R1 及之后（core 没有 asset），因此 **core 的判定逐条不变**。

| # | 阶段 | 检查 | 码 |
|---|---|---|---|
| 1 | core 阶段 2 | UTF-8 可解码（允许并忽略 BOM） | `PXL001` |
| 2 | **current 阶段 D** | 通用 JSON 对象检查（合法 JSON、成员名不重复，二者都与版本无关）；随后读 `format` 与 `version` 并分派（Extension §2） | `PXL001` / `PXL007` |
| 3 | **current 阶段 P** | 参数声明语法、参引语法、bindings 集合与类型、白名单外的参引；通过后**完成替换**（Extension §6.5） | `PXL012` |
| 4 | core 阶段 3 | 成员集合（Extension §3.2 表）、类型类别、`format`/`version` 的具体值、图层名、`layers` 非空、已知 op 的参数集合（含 `stamp` 的 `sprite`/`asset` 恰一）、行数组形状、`assets`/`params` 的成员集合与名字语法 | `PXL001` |
| 5 | core 阶段 4 | `encoding` 取值 | `PXL003` |
| 6 | core 阶段 5 | 依赖 token 宽度的检查（行字符数、token 字符集） | `PXL001` |
| 7 | core 阶段 6 | 数值域：文档级（含 Extension §10.1 的全部上界）与 op 级 | `PXL002` |
| 8 | core 阶段 7 | `encoding` 与 palette 长度派生的一致性 | `PXL003` |
| 9 | core 阶段 8 | op 名是否在八条之内 | `PXL004` |
| 10 | core 阶段 9 | 引用与容量：palette 格式与长度、数值 slot、token 解出的 slot、`stamp` 的 sprite/asset 名是否存在 | `PXL005` |
| 11 | **current 阶段 R1** | 每个 asset 声明的逻辑路径语法与规范化（Extension §7） | `PXL008` |
| 12 | **current 阶段 R2** | 按 Extension §9.3 的固定顺序解析**被选中**的依赖：resolver 结果映射（Extension §8.2）；被引用文档从**它自己的**阶段 1 起完整再跑一遍（其 `PXL001`..`PXL012` 原样传播并加引用链） | `PXL009` / `PXL008` / `PXL007` / 被引用文档的码 |
| 13 | **current 阶段 R3** | 循环检测（Extension §9.2） | `PXL010` |
| 14 | **current 阶段 R4** | 会话预算（Extension §10.2），按表内顺序判定：深度 → 节点数 → 文件数 → 累计字节 → 累计像素 → 全局光栅 | `PXL011` |
| 15 | —— | 光栅化与 PNG 编码 | 不产生 PXL 码 |

四条由此固定的边界，实现不得另选：

- **阶段 R1 为什么排在 core 阶段 9 之后**：把 current 的路径校验放在 core 全部九阶段之后，core 文档的错误码与
  优先级就逐条不变（PRD Extension §6.1 的硬要求）。同一份 current 文档若同时有 palette slot 越界与非法 asset 路径，
  报 `PXL005`（阶段 10 先于 11）。
- **阶段 R2 先于 R4**：先解析依赖、后判会话预算，这样"依赖不存在"（`PXL009`）不会被误报成
  "预算超限"（`PXL011`）。
- **阶段 P 为什么在阶段 4 之前**：PRD Extension §10.5 要求参数阶段位于版本分派之后、具体字段值校验之前；
  替换完成后的具体文档才进入 core 阶段 3 起的字段校验，于是"替换后的字段错误按目标字段原码报"
  （Extension §6.5 的四条判定即由此而来）。
- **预算已超之后不再解码后续 PNG**：那些 PNG 的结构错误（`PXL006`）因此不再被枚举——它们本属
  R2，而"超限即拒、不再解码"意味着这个 target 报的是 `PXL011`；与此同时，**已解析文档**的
  `PXL009`/`PXL008` 仍优先（R2 里读到的文件照旧按 R2 判）。

- JSON 嵌套层数上限 **128**（超出为 `PXL001`）：这是解析器的资源边界，不是语言特性；  两个实现必须取同一个值，否则同一份文档会在两侧得到不同错误码。

## Extension §12. 确定性

相同语言版本、入口字节、实际依赖字节与规范 bindings 必须产生相同 RGBA8；同一 compiler 构建、
同一声明运行时、同一输入，两次输出 PNG 字节必须相同。结果不得受 locale、时区、当前目录、
文件系统遍历顺序、随机数、时钟、进程 ID、缓存命中、哈希表迭代顺序、宿主大小写宽容或错误遍历的
偶然顺序影响。PNG 压缩参数固定。

## Extension §13. 语料、能力档案与测试边界

### Extension §13.1 版本隔离

current 语料放在 `spec/conformance/current/`，与 core 的 `CASES.tsv` + `cases/` **互不重叠**；current 语料
**不得**改变 core 的任何期望值（包括 `version: 1 `→`PXL001` 的 version gate 专属负例）。

### Extension §13.2 能力档案与 profile

实现通过统一 CLI 暴露机器可读能力档案（PRD Extension §6.3 的 schema version 1），conformance runner 先读档案、
再按 `spec/conformance/profiles.tsv` 选出**唯一**语料集合。`profiles.tsv` 是四列
`profile<TAB>suite<TAB>action<TAB>case`，集合代数固定为"并集减精确排除"，不接受 glob、
正则、目录隐式递归或实现私有条件。

### Extension §13.3 current 用例形态

current 索引**不复用** core 的目录前缀推断，每行显式声明 `form`：`single` / `graph` /
`bindings` / `negative`。用例目录可含 `entry.pxl`、`assets/`、`bindings.json`、
一份或多份 `expected.pixels.sha256`、`expected.dependencies.tsv`、`expected.error`、`notes.md`。
current 语料**不含** PNG→PXL 往返正例（Importer 只产 core）。

#### Extension §13.3.1 用例目录即 asset root

current 用例目录**就是**该用例的 asset root，入口逻辑路径**恒为** `entry.pxl`。被引用的外部素材按
**其逻辑路径**原样放在用例目录里：逻辑路径 `parts/blade.pxl` 对应 `<case>/parts/blade.pxl`。
PRD Extension §18.2 的清单里列了 `assets/` 这一项，本规范**明确不采用**——逻辑路径本身已经是相对路径，
再套一层 `assets/` 只会制造第二套映射，而且会让"引用相对声明它的文档所在目录"这条（Extension §7）失效。

例（`form: graph` 的最小目录）：

```text
<case>/entry.pxl            逻辑路径 entry.pxl，内部 asset 声明 path: "parts/blade.pxl"
<case>/parts/blade.pxl      逻辑路径 parts/blade.pxl
```

#### Extension §13.3.2 内存 resolver 的拼写声明

默认情况下内存 resolver 的"实际拼写"取磁盘拼写。**只有** `CASE_MISMATCH` 用例需要二者不同：
这类用例在目录里放 `spelling.tsv`，两列 `logical<TAB>actual`，声明"按逻辑路径查找时应按
`actual` 的拼写命中、但拼写与逻辑路径不一致"的条目；`actual` 必须是同目录下真实存在的文件。
存在 `spelling.tsv` 时 resolver 先按它回答，未列出的逻辑路径按常规处理。这样大小写规则在
**平台无关**的语料里可判定（PRD Extension §13.2），不依赖宿主文件系统是否大小写敏感。

#### Extension §13.3.3 `bindings.json`

`bindings.json` 是**载体**，任何 `form` 都可以放它——参数类负例同样需要一组绑定（`PXL012` 的「缺必需参数」只能由一组 bindings 触发）。它与 `form` 的分工是：放不放由「这条用例要不要绑定」决定；`form: bindings` 额外要求**至少两个** target 且每个 target 都有期望像素。

形状：

```json
{"targets": [{"name": "copper", "bindings": {"base_color": "B87333FF"}},
             {"name": "iron",   "bindings": {"base_color": "D8D8D8FF"}}]}
```

每个 target 的期望像素写在 `expected.<name>.pixels.sha256`（一行小写 SHA-256 + LF）。`name` 必须
匹配 `[a-z][a-z0-9_-]*` 且在文件内唯一；缺少任一 target 的期望文件即**用例自身非法**。

#### Extension §13.3.4 期望文件的格式

- `expected.pixels.sha256`：一行小写十六进制 + 一个 LF，口径同 Core §13.4（RGBA8 原始字节流的 SHA-256）；
- `expected.error`：一行，内容**恰好**是错误码（例如 `PXL009`），不带说明文字——说明写 `notes.md`；
- `expected.dependencies.tsv`：**不带表头行**。Extension §9.4 规定"第一行必须是唯一入口"，表头会与这条直接冲突；
  四列按 Extension §9.4 的定义与排序逐字节写出。

#### Extension §13.3.5 索引列

current 索引每行**至少**声明 `case`、`form`、`defect`、`expected`、`notes` 五列；允许另加**说明性**列（例如 `covers`），但 runner 的判定不得依赖说明性列，只认这五列。`defect` 取值限于
`structure` / `params` / `version` / `path` / `dependency` / `cycle` / `budget` /
`png` / `render` / `priority`：`form: negative` 时必需（机械标记该负例的缺陷类别），其余形态写 `-`。

`priority` 专给「刻意让两条规则同时成立、只允许较高优先级那条生效」的冲突例（例如参数替换后 `slot` 越界必须报 `PXL005` 而不是 `PXL012`）：它的缺陷既不属于单纯 params 也不属于单纯结构，单列一类。
索引整体**就是** `profiles.tsv` 里的 `current` 这一 suite，不再逐行重复声明 suite。
`expected` 列列出该用例目录里实际出现的期望文件与入口，使"目录里有什么"与"索引声称有什么"可机械比对。

#### Extension §13.3.6 命名与 suite 边界

- 刻意违反多条规则的负例沿用 core 的 `neg-priority-*` 命名；
- `version gate` 是**独立 suite**，不属于 current suite，其输入文件名沿用 core 负例的 `input.pxl`；
- 每个用例目录必须有 `notes.md`：写明覆盖的条款、期望值怎么来的（若由 oracle 算出，要写明用了哪个
  模块与哪条等价关系）、以及与 core 的任何差异。

#### Extension §13.3.7 pending 用例（阶段性占位）

阶段 2/3/4 的实现尚未落地时，有些用例的正确期望值**还算不出来**（例如依赖 asset 渲染的正例）。这类用例
可以存在，但必须三条同时成立，缺一条即用例非法：

1. 索引的 `expected` 列写 `-`（不得声称有期望文件）；
2. 索引的 `notes` 列以 `pending:` 开头，后接卡在哪个阶段；
3. 用例目录里**没有**任何 `expected.*` 文件，但 `entry.pxl` 必须存在，且它的 `notes.md` 首段写明阻塞原因。

pending 用例**不计入**通过数，也不得被报告成「已通过」。**发布门禁**：把能力档案改成 `vnext-core-current` 之前（PRD Extension §6.4），每一个 `pending:` 都必须清零——否则「current 语料完整通过」这句话里有一半是空的。

### Extension §13.4 reference oracle

current reference oracle **必须 import** core oracle 的八条 op、裁剪、Bresenham、三种 blend 与像素摘要实现，
只新增版本分派、resolver、依赖图、asset stamp、bindings、预算与错误优先级；**不得**复制一份 core 光栅
算法后独立漂移。复用不违反"独立 oracle"：core oracle 不 import Importer 或任何 compiler 生产代码。

### Extension §13.5 永久双路径 PNG 门禁

core 的全部 `neg-png-*`、其他 `PXL006` 负例与 Core §8.5 的接受集，**既**在 Importer decoder 上执行，
**也**在每个支持 PNG asset 的 compiler decoder 上执行，接受例解出的 RGBA8 必须一致。该门禁只在
conformance/测试层调用 Importer，**不建立** compiler 到 Importer 的生产期依赖。

## Extension §14. 保留与延期

以下能力**不属于** PXL current，遇到即按下列方式拒绝或忽略：

- 16-bit 通道、Adam7 交错、色彩管理：按 Core §8.3 拒绝（`PXL006`）；
- Unicode 或大写逻辑路径、Windows 反斜杠、绝对路径、URL、glob：按 Extension §7 拒绝（`PXL008`）；
- 动态路径、条件依赖、参数构造路径、网络与包管理器 asset：不提供，出现即 `PXL012` 或 `PXL008`；
- 任意参数表达式、数组/对象参数、用户函数、循环、递归、条件分支：不提供；
- 缩放、任意角度旋转、插值、抗锯齿、浮点颜色：不提供；
- 读取被引用文档的内部图层或 sprite：不提供（Extension §5.3）；
- 文档内 `variant` 语义与文档指定的输出路径：不提供；`variant` 出现即 `PXL001`；
- 一个核心编译调用写出多个文件：不提供（PRD Extension §7）；
- 跨运行时位精确 PNG 压缩：不承诺（PRD Extension §14.2）。
